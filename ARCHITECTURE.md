# curlPro — the architecture

A Python library for HTTP requests that forge a browser's network fingerprint.
The governing requirement: **a new Chrome or Firefox profile is added by editing
data, without rebuilding native code.**

Neighbouring documents: [RESEARCH.md](docs/RESEARCH.md) — the existing solutions
analysed from their sources, [FINGERPRINT-SPEC.md](docs/FINGERPRINT-SPEC.md) —
the fingerprint formats, [CAPTURE.md](docs/CAPTURE.md) — capturing references,
[PROFILE-SCHEMA.md](docs/PROFILE-SCHEMA.md) — the profile schema,
[ROADMAP.md](ROADMAP.md) — the stages.

> This document was written at the start of the work and describes the
> **intent**. Where the intent diverged from what came out, the divergence is
> marked in the text itself.

## Why not a curl_cffi fork

The research showed that the curl-impersonate path does not satisfy the main
requirement:

- The browser profiles are ~2367 lines of C structures in `lib/impersonate.c`,
  generated by the `patches/curl.patch` patch. Adding Chrome 150 means +84 lines
  of C and a BoringSSL rebuild.
- A runtime path does exist (the `Fingerprint` dataclass in
  `curl_cffi/fingerprints.py`, ~40 setopt calls, covering the whole C struct),
  but it is fed from `https://api.impersonate.pro/v1/fingerprints` under an
  `IMPERSONATE_API_KEY`. Open source gets its updates "on major releases".
- That is, precisely the part we want to control is monetised.

Further hard limits of a BoringSSL fork, had we taken that road: the TLS 1.3
cipher order is compared by `strncmp` against six hard-coded permutations
(everything else falls silently back to `kCiphersAESHardware`); the GREASE
positions are compiled in; and the HTTP/2 frame order is exposed by no CURLOPT at
all.

## The chosen stack

```
Python (ctypes)  →  libcurlpro.{so,dll,dylib}  →  Go
                                                   ├── uTLS         ClientHello
                                                   ├── fhttp        HTTP/1.1 and HTTP/2
                                                   ├── uquic        QUIC
                                                   ├── internal/h3  HTTP/3 (vendored)
                                                   └── internal/qpack  our own QPACK
```

Go was chosen for two uTLS capabilities that answer the updatability requirement
directly:

1. **`ClientHelloSpec.UnmarshalJSON`** — a native JSON codec. A profile lives in
   a `.json` file and is loaded at runtime. A named dictionary (`dicttls`) rather
   than magic numbers.
2. **`Fingerprinter.RawClientHello(raw []byte)`** — reconstructs a
   `ClientHelloSpec` from captured ClientHello bytes. It closes the loop:
   capture a browser, get a profile.

Rust (`wreq`/`rquest`) reaches the same fingerprint quality but has no equivalent
of the second point, and its profiles are Rust code as well.

## The profile model: JSON with inheritance

The schema is borrowed from `sardanioss/httpcloak` (MIT), where it had already
proven itself: a routine Chrome bump that changes only the UA and the sigalgs is
~40 lines of JSON.

```jsonc
{
  "version": 1,
  "preset": {
    "name": "chrome-152-windows",
    "based_on": "chrome-151-windows",     // a delta over the parent
    "tls": {
      "signature_algorithms": [2308, 2309, 2310, 1027, ...],  // 0x0904 = ML-DSA-44
      "trust_anchors": ["82df130201", ...]                     // ext 0xCA34, new in Chrome 152
    },
    "headers": {
      "user_agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...",
      "order": [ {"key": "sec-ch-ua", "value": "..."}, ... ]
    }
  }
}
```

Three levels of loading:
- the profiles ride inside the wheel, and `ensure_loaded()` picks them up at the
  first request
- a directory of your own — `curlpro.load_profiles("profiles")`
- `curlpro.register_profile()` from Python — registration at runtime

The last one matters: a user can roll out Chrome 153 on their own machine without
waiting for a release of ours.

The intent was different: into the binary through `//go:embed`. It was not done
that way — the profiles are shipped as data inside the package and read from
disk. There is not one `go:embed` in the repository.

## What the profile covers

| Layer | Fields |
|---|---|
| TLS | ciphers, extensions + order, curves, sigalgs, ALPN, ALPS (17513/17613), cert_compression, key_share, permute_extensions, record_size_limit, trust_anchors |
| HTTP/2 | settings + **order**, connection_window_update, priority frames, pseudo_header_order, header_order, stream_weight/exclusive |
| HTTP/3 | qpack parameters, quic_transport_params + order, grease frames |
| Headers | the set, the order, the case, client hints |

## The boundary: what still requires Go changes

Not every new browser is data-only. Code is needed for:

- **a new type of TLS extension** — a `TLSExtension` with `UnmarshalJSON`
  (Chrome 152 brought `trust_anchors` 0xCA34; Chrome 150 brought the ML-DSA
  sigalgs)
- **ECH and the QUIC transport parameters** —
  `GREASEEncryptedClientHelloExtension` and `QUICTransportParametersExtension` do
  not implement `UnmarshalJSON` in upstream uTLS. A post-processor is needed, one
  that splices in `BoringGREASEECH()` for Chrome ≥120.

The frequency is once every 6–12 months rather than every 4 weeks. That is
acceptable.

## The reference-capture pipeline

```
1. echo-server (wi1dcard/fingerproxy) on :8443, a self-signed cert
2. Chrome with --host-resolver-rules="MAP www.example.com 127.0.0.1:8443", >=5 runs
3. GET /json/detail -> the raw ClientHello record in base64 + parsed JA3/JA4 + H2 frames
4. in parallel tshark + SSLKEYLOGFILE -> the H2 frames and the header order
5. utls.Fingerprinter.RawClientHello() -> ClientHelloSpec -> serialised into our JSON
6. validation: replayed against tls.browserleaks.com, JA3N/JA4/akamai_text compared
```

The starting corpus: `lexiforest/curl-impersonate/tests/signatures/*.yaml` — 43
files, Chrome 98–150, Safari 15–26, Firefox, Edge, Tor, with JA3/JA3N/Akamai
hashes already computed.

## Traps (found during the research; they cost other projects bugs)

- **PRIORITY weight = wire_value + 1** (RFC 7540). The commonest mistake in other
  implementations.
- **WINDOW_UPDATE serialises as `%02d`** — an absent one gives `00`, not `0`.
- **Chrome ≥110 shuffles its extensions.** Five consecutive captures give 5
  different JA3 values and 1 identical JA4. Build a profile only from the
  normalised form, from at least 5 samples.
- **`ShuffleChromeTLSExtensions` mutates the slice in place.** A cached spec is a
  frozen order on every connection, which is an anomaly in itself. Derive it
  afresh per connection.
- **A post-quantum key_share (~1216 bytes) splits the ClientHello across two TCP
  segments.** In tshark take `tcp.reassembled.data`, not `tcp.payload` — the
  latter truncates silently.
- **SNI affects JA4:** connecting by IP changes `d` to `i` and the extension
  count. Use `localhost` or host-resolver-rules, never a bare IP.
- **The services disagree about computing JA3/JA4.** browserleaks is the
  reference; scrapfly uses `supported_versions` instead of the legacy version in
  JA3 and sorts the sigalgs against the specification.
