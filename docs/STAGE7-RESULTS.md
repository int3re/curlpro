## Две гонки, видимые только вживую

Отпечаток сначала совпадал не в каждом запросе. Причины оказались разные,
и обе не воспроизводятся на локальном стенде.

**Управляющий поток уходил параллельно запросу.** Апстрим открывает его
в горутине, а запрос отправляется сразу; это разные потоки QUIC, и сервер
успевал ответить, не увидев SETTINGS. Браузер открывает управляющий поток
до первого запроса — теперь первый запрос его ждёт.

**PRIORITY_UPDATE адресован потоку, а не соединению.** Кадр несёт идентификатор
потока, поэтому Chrome отправляет его перед каждым запросом. Одна отправка
с нулём давала совпадение **только для первого запроса** — картина «1 из 5»
и вывела на причину.

## Дефект: ответы портились дважды

Первая версия распаковки сломала все запросы к browserleaks
(`magic number mismatch`). Оказалось, `fhttp` **сам распаковывает всё** —
gzip, deflate, br и zstd, — но не удаляет `Content-Encoding` и не ставит
`Uncompressed`. Распаковка работала поверх уже распакованного.

Своя распаковка нужна только на пути HTTP/3, где стоит `net/http`: тот знает
лишь gzip и только когда сам поставил заголовок. Перенесена туда.

Дефект дважды не проявлялся на httpbin, потому что тот отдавал несжатое.

## Долг: priority на HEADERS-кадре

Было: 43 профиля из 44 не задавали `stream_weight`, и библиотека подставляла
дефолт `255, exclusive` — случайно верный для Chrome и неверный для остальных.

| семейство | вес | exclusive |
|---|---|---|
| Chrome, Edge | 256 | да |
| Firefox, Tor | 42 | нет |
| Safari | **не отправляет** | — |

Для «не отправлять» нашёлся способ: нулевой `PriorityParam` не выставляет флаг,
тогда как `nil` заставил бы библиотеку подставить дефолт.

**Проверять пришлось на третьем оракуле.** Два первых дали противоречивую
картину: browserleaks показал `0` у всех профилей (он учитывает только
самостоятельные PRIORITY-кадры), стенд fingerproxy — `1:0:0:256` даже
для Safari (подставляет дефолт, когда флага нет). Разрешила покадровая
разбивка `fp.impersonate.pro`:

```
Chrome: flags [EndStream, EndHeaders, Priority (0x20)], {weight: 256, exclusive: 1}
Safari: flags [EndStream, EndHeaders]                    ← флага Priority нет
```

## Долг: схлопывание профилей

Импорт корпуса дал самодостаточные профили, и они сильно дублировали друг друга:
**44 профиля при 24 уникальных ClientHello**.

`curlpro collapse` сгруппировал их и переписал 20 штук как дельты:

```
chrome-98-windows  <- 11 профилей (Chrome 99–116, Edge 98–101)
safari-18.0-ios    <- 3
chrome-133-macos   <- 2 (Chrome 136, 142)
safari-15.5-macos  <- 2
```

Каталог сократился со 161 до 116 КБ, **все 44 отпечатка не изменились**.

Главная польза не в размере, а в наглядности. Вот весь профиль Chrome 110
после схлопывания:

```json
{
  "based_on": "chrome-98-windows",
  "name": "chrome-110-windows",
  "tls": { "permute_extensions": true },
  "headers": { … }
}
```

Вся разница между Chrome 98 и 110 на уровне TLS — это `permute_extensions`,
то есть ровно тот момент, когда Chrome начал перемешивать расширения.
Дельта-модель, ради которой строилась схема, подтвердилась на данных.

## Осталось

- **Динамическая таблица QPACK.** Мы объявляем ёмкость, как Chrome, но декодер
  её не поддерживает: сервер, который ей воспользуется, вернёт неразбираемый
  ответ. Наблюдалось на `fp.impersonate.pro` со второго запроса.
- **Порядок в version_information** — единственное неразрешённое разногласие
  между utls и curl-impersonate, вынесено в настройку профиля.
- **Отпечаток HTTP/1.1 не проверялся**: стенд считает только h2-часть.
- **Потоковая отправка тела** — большой файл целиком попадает в память.
