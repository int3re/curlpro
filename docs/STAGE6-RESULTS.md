# Этап 6 — инструменты сопровождения

Дата: 2026-09-01. Сделаны `validate`, `diff`, `list`. `capture` пока нет.

## Зачем

До этого этапа **23 профиля из 44 не были сверены ни с чем**: в корпусе
curl-impersonate у них нет эталонных хешей, проверялось лишь то, что спека
собирается. Профиль мог давать чужой отпечаток, и заметить это было нечем.

## `curlpro validate`

Прогоняет профили через оракула и сверяет отпечаток с записанным эталоном.

```
curlpro validate -oracle https://localhost:8443/json -insecure \
                 -baselines reference/baselines-local
```

Оракулом может быть `tls.browserleaks.com` или локальный echo-server; форматы
ответов различаются, разбираются оба. Для массового прогона по 44 профилям
опорным сделан локальный стенд: внешний сервис на серии запросов срывается
(первый же прогон дал таймаут на втором профиле). Ретраи с нарастающей паузой
добавлены, но полагаться на чужую сеть в регрессии не стоит.

Для профилей без внешнего эталона работает вторая линия: отпечаток снимается
один раз и фиксируется, а последующие прогоны ловят регрессии в нашем коде.

## Найденный баг: два профиля не работали вовсе

Первый же полный прогон:

```
ОШИБКА chrome-119-macos  TLS handshake: tls: empty psk detected;
                         remove the psk extension ... or set OmitEmptyPsk
ОШИБКА chrome-120-macos  то же
```

Это ровно те два профиля, что содержат `pre_shared_key` — они сняты
с возобновлённого соединения. На первом соединении тикета нет, и uTLS
отказывается слать пустое расширение.

Браузер в этой ситуации расширение просто не шлёт, что и делает
`Config.OmitEmptyPsk`. После правки работают все 44.

Показательно, что дефект прожил три этапа: тесты гоняли Chrome 151, Firefox
и Safari, а до этих двух профилей очередь не доходила. Массовый прогон нашёл
его за один запуск.

## Колеблющийся JA4 — и почему это не баг

Второй прогон показал, что `chrome-119-linux` и `edge-120-linux` дают то
16, то 17 расширений:

```
t13d1516h2_8daaf6152771_02713d6af862
t13d1517h2_8daaf6152771_b1ff8ab2d16f
```

Причина: у обоих есть расширение `padding`. BoringSSL добавляет его, только
когда длина ClientHello попадает в диапазон 256–511, а тело второго GREASE
бывает пустым или в один байт — этого достаточно, чтобы перейти границу.

**Настоящий Chrome ведёт себя так же**, поэтому фиксировать одно значение было
бы неверно: эталон хранит множество допустимых JA4, а `-update` пополняет его,
а не затирает. Из 44 профилей колеблются ровно два — оба с `padding`.

Это третий по счёту случай в проекте, когда «нестабильность» отпечатка
оказалась верным воспроизведением браузера, а не дефектом: до этого были
перемешивание расширений (этап 0) и рандомизация GREASE.

## `curlpro diff`

Показывает, чем два профиля различаются: расширения сравниваются как множества
(порядок у Chrome перемешивается), остальное — последовательностями.

```
$ curlpro diff chrome-133-macos chrome-150-macos
user-agent:
  - ... Chrome/133.0.0.0 ...
  + ... Chrome/150.0.0.0 ...

sigalgs:
  - 1027 2052 1025 1283 2053 1281 2054 1537
  + 2308 2309 2310 1027 2052 1025 1283 2053 1281 2054 1537
```

Семнадцать мажорных версий Chrome развели ровно два поля — User-Agent
и добавленные ML-DSA. Это и есть та дельта-модель, ради которой строилась
схема профиля: наглядное подтверждение, что `based_on` покроет большинство
обновлений.

## `curlpro list`

Перечисляет профили с источником ClientHello (`raw` или `extensions`)
и количеством расширений, заголовков и настроек HTTP/2.

## `curlpro capture`

Снятие эталона стало одной командой вместо четырёх скриптов и ручных шагов:

```
$ curlpro capture -name chrome-151-recapture -samples 5
стенд:    echo-server_windows_amd64.exe на localhost:8443
сэмплов:  5
  сэмпл 1/5 … 5/5
собрано: 5 сэмплов, расширений 18, заголовков 13, ClientHello 1725 байт
профиль записан: profiles/chrome-151-recapture.json
```

Команда поднимает стенд как подпроцесс, читает его вывод, приводит браузер
с одноразовым профилем на каждый заход (иначе соединение переиспользуется
и перестановка не меняется), отбирает сэмплы по `:path` и сводит их в профиль.

Встроенные проверки:
- **favicon отбрасывается** — он приходит по тому же соединению, но с другими
  `sec-fetch-*`, и попал бы в профиль вместо навигационного запроса;
- **наборы расширений без GREASE обязаны совпасть** между сэмплами, иначе
  захват шёл с разных браузеров и профиль будет смесью;
- вес приоритета с HEADERS записывается с поправкой `+1` (RFC 7540).

### Проверка цикла

Chrome 151 снят заново и сопоставлен с профилем, полученным вручную на этапе 0:

```
$ curlpro diff chrome-151-windows chrome-151-recapture
профили совпадают по всем сравниваемым полям

JA4 обоих: t13d1516h2_8daaf6152771_806a8c22fdea
```

То есть автоматический захват воспроизводит результат ручного, полученного
четырьмя скриптами месяцем ранее.
