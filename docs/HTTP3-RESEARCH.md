# HTTP/3: разведка перед реализацией

Состояние на 2026-09-01.

## Главный вывод

Ни одна библиотека не покрывает оба слоя. Отпечаток H3 складывается из двух
независимых частей, и проекты закрывают либо одну, либо другую:

| | QUIC-слой (Initial, transport parameters) | H3-слой (SETTINGS, псевдо-заголовки) |
|---|---|---|
| `refraction-networking/uquic` | **да** — `QUICSpec`, парроты Chrome 115/146 | нет, стоковый quic-go |
| `bogdanfinn/quic-go-utls` | нет, стоковый quic-go | **да** — порядок SETTINGS, GREASE, PRIORITY_UPDATE |
| `sardanioss/httpcloak` | да | да | — но вертикальный форк из шести репозиториев, несовместим с нашим стеком |

Наш стек — `refraction-networking/utls` + `bogdanfinn/fhttp`. Отсюда план:
**uquic для QUIC-слоя + собственные правки H3-слоя**.

## Оракулы: какой что покрывает

Проверено живым H3-запросом (`cmd/h3probe`).

`quic.browserleaks.com/json` **редиректит на `/fp`** — путь `/json`, гуляющий
по статьям, устарел. Отдаёт JA4-q и `h3_text`, то есть только H3-слой.

**`fp.impersonate.pro/api/http3` — единственный, кто отдаёт разобранные
transport parameters**, то есть покрывает и QUIC-слой. Его формат `perk`
состоит из **четырёх** секций, а не трёх, как в документации curl_cffi:

```
SETTINGS | псевдо-заголовки | transport parameters | длины CID
```

Нормализация продумана и делает `perk_hash` пригодным для CI: GREASE-записи
сворачиваются в литерал `GREASE`, случайный `initial_source_connection_id`
(id 15) заменяется на `AUTO`, `version_information` (id 17) печатается
как `chosen@available,…`.

Отдельно: **JA4-q покрывает только TLS ClientHello внутри QUIC Initial.**
Буква `q` — единственный вклад транспорта. Ни transport parameters, ни SETTINGS
в JA4 не входят, и аналога JA4T для UDP не существует. Значит проверять эти
слои можно только проприетарными строками.

## Замер: что даёт uquic из коробки

```
$ go run ./cmd/h3probe -url https://fp.impersonate.pro/api/http3
паррот: chrome146
  SCID/DCID: 0 / 8      первый пакет: номер 1, длины [1 2]

HTTP 200 OK (HTTP/3.0)   CID клиент/сервер: 0/8
perk: 6:10485760|a,m,p,s|5:6291456;1:30000;32:65536;8:100;15:AUTO;
      12584:0x31304146;9:103;GREASE;16741339:1@GREASE,1;6:6291456;
      12583:AUTO;4:15728640;7:6291456;3:1472|0,8
```

### QUIC-слой: было три расхождения, осталось одно спорное

Сверка с `chrome150` из curl-impersonate — **все основные значения совпадали
сразу**: `1:30000`, `3:1472`, `4:15728640`, `5/6/7:6291456`, `8:100`, `9:103`,
`32:65536`, пустой SCID, длины CID `0/8`.

Расходились ровно три вещи, и все три — из списка спорных выше:

| | uquic было | Chrome | после правки |
|---|---|---|---|
| `12584` google_connection_options | `"10AF"` | `"ORIG"` | ✅ `0x4f524947` |
| `12583` google_initial_rtt | шлёт | не шлёт | ✅ убран |
| version_information ID | **16741339** (черновой `0xFF73DB`) | **17** (`0x11`) | ✅ `17` |
| version_information порядок | `GREASE,1` | `1,GREASE` | ⚠️ спорно |

Правки сделаны через модификацию `ClientHelloSpec` (см.
[internal/profile/quic.go](../internal/profile/quic.go)) — патчить uquic
не потребовалось: transport parameters доступны как обычный слайс,
а `FakeQUICTransportParameter` служит запасным выходом для любых значений.

**Оставшееся расхождение не разрешено и вынесено в настройку профиля.**
Документация utls прямо утверждает, что Chrome ставит GREASE первым, и паррот
uquic делает так же; curl-impersonate записывает `1,GREASE`. Возможно, дело
в нормализации при сериализации в строку, а не в реальном порядке байт.
Разрешается только собственным захватом.

Итог сверки 13 параметров: **12 совпадают, 1 спорный**.

### H3-слой: не совпадал ничем — исправлено

| | uquic было | Chrome 144 | после правок |
|---|---|---|---|
| SETTINGS | `6:10485760` | `1:65536;6:262144;7:100;51:1;GREASE` | ✅ |
| псевдо-заголовки | `a,m,p,s` | `m,a,s,p` | ✅ |
| GREASE-кадр | нет | есть | ✅ |
| PRIORITY_UPDATE | нет | `984832` | ✅ |

Публичное API `http3.Transport` даёт только `AdditionalSettings map[uint64]uint64`
(без порядка — map!) и `EnableDatagrams`, поэтому пакет вендорен
в [internal/h3](../internal/h3/). Итог совпадает с Chrome байт-в-байт
и стабилен на повторных прогонах:

```
1:65536;6:262144;7:100;51:1;GREASE|GREASE|984832|m,a,s,p
```

Устройство правок — [internal/h3/README.md](../internal/h3/README.md).

## Про порядок transport parameters

Популярные статьи утверждают, что порядок — часть отпечатка. Первоисточники
для Chrome говорят обратное: uquic документирует `RandomizeTransportParameters`
как «повторяет реальный Chrome, который перемешивает порядок на каждом
рукопожатии», а `clienthellod` намеренно **сортирует** ID перед хешированием.

То есть для Chrome аномалией является как раз **фиксированный** порядок.
Сверять надо отсортированный набор ID, значения, число GREASE, длину DCID,
номер первого пакета (1, а не 0) и размер датаграммы. Для Firefox порядок
фиксирован, и там он значим.

## Значения Chrome

**HTTP/3 SETTINGS:** `1:65536` (QPACK max table), `6:262144` (max field section),
`7:100` (QPACK blocked streams), `51:1` (H3_DATAGRAM), плюс одна GREASE-запись
(`0x1f*N + 0x21`). Порядок `[0x01, 0x06, 0x07, 0x33, GREASE]`.

**Firefox:** `1:65536;7:20;727725890:0;16765559:1;51:1;8:1` — blocked streams 20,
объявляет WebTransport, GREASE не шлёт.

**Псевдо-заголовки:** Chrome `m,a,s,p`, Firefox `m,s,a,p`.

**PRIORITY_UPDATE:** Chrome шлёт тип `0xF0700` (984832) с телом
`varint(0) + "u=0, i"`. Firefox не шлёт.

**QUIC transport parameters Chrome** (curl-impersonate `chrome150`):
```
1:30000;3:1472;4:15728640;5:6291456;6:6291456;7:6291456;8:100;9:103;
15:;17:1@1,GREASE;32:65536;12584:0x4f524947;GREASE
```

**Connection ID:** Chrome — SCID пустой, DCID 8 байт. Firefox — SCID 3,
DCID 8/9/15 (разные значения дают разные отпечатки, uquic держит три паррота).

**Initial-пакет:** номер начинается с **1**, а не с 0; длины номеров `[1, 2]`;
ClientHello фрагментируется по многим CRYPTO-кадрам вперемешку с PING и PADDING;
post-quantum key share вынуждает **две Initial-датаграммы**.

## Формат `perk` (curl_cffi)

`HTTP3_SETTINGS | PseudoHeaderOrder | QUICTransportParameters` — три поля через
`|`, аналог четырёхполевой строки `akamai` для H2. Значения параметров имеют
пять особых форм помимо десятичной: пустая (`15:`), `AUTO`, `v@list`
(`17:1@1,GREASE`), шестнадцатеричная (`12584:0x4f524947`) и голое `GREASE`.

Смысл принять этот формат у себя: он позволяет напрямую импортировать четыре
известных строки из curl-impersonate.

## Разногласия, которые придётся разрешать захватом

Реализации противоречат друг другу по текущему Chrome — это не мелочь,
а прямой риск взять чужую ошибку за истину.

| Вопрос | Позиции |
|---|---|
| `0x3127` google_initial_rtt | uquic шлёт («новое в Chrome 146»); httpcloak **убрал**, утверждая, что реальный Chrome 151 его не шлёт, а генерация требовала лишнего TCP-соединения, которое само по себе примета |
| `0x3128` google_connection_options | `"RVCM"` (uquic 115), `"10AF"` (uquic 146), `"B2ON"` (azuretls), `"ORIG"` (httpcloak, ссылаясь на дефолт Chromium `kQuicOptions`) |
| порядок в `version_information` | uquic: `[GREASE, 1]`; curl-impersonate: `1,GREASE` |

Значение `0x3128` — параметр Finch, а не константа версии: у одной и той же
сборки Chrome 152 встречаются и `"ORIG"`, и `"IW50,ORIG"`. Значит это поле
профиля, а не константа в коде.

Про `"B2ON"` у azuretls httpcloak отмечает, что оно появляется только при явном
`--enable-features=QuicConnectionOptions=B2ON` и «заставляет некоторые
QUIC-детекторы молча отбрасывать последующие кадры».

Паррот `QUICChrome_146` в uquic выведен из **одного** pcap-сэмпла. Наш опыт
с TCP-слоем (этап 0) показал, что одного захвата недостаточно даже для
расширений; для QUIC оснований доверять единственному сэмплу не больше.

## Чему нельзя верить

- **CycleTLS** — заглушка: `CreateUQuicSpecFromFingerprint` и `...FromJA4`
  игнорируют аргумент и всегда возвращают Chrome 115 (комментарий в коде:
  «once I find a route to test against»).
- **enetx/surf** — QUIC-фингерпринтинг удалён коммитом `remove uquic`
  (2025-12-31), значения закомментированы, но README по-прежнему обещает
  «Full Chrome and Firefox QUIC transport parameter matching».
- **`go get uquic@latest`** — даст тег v0.0.6 от 2024 года с Chrome 115.
  Работа над Chrome 146 живёт только в master, нужна псевдо-версия.

## Оракул

`https://quic.browserleaks.com/` возвращает:

```json
{ "h3_hash": "ba909fc3dc419ea5c5b26c6323ac1879",
  "h3_text": "1:65536;6:262144;7:100;51:1;GREASE|GREASE|984832|m,a,s,p" }
```

Формат: `SETTINGS | GREASE-кадр | PRIORITY_UPDATE | порядок псевдо-заголовков`.

Важное ограничение: **`h3_text` покрывает только H3-слой**. Transport parameters
и структуру Initial-пакета он не показывает — для них нужен разбор pcap.
То есть автоматическая проверка возможна лишь для половины отпечатка.

## Ограничения корпуса

В `curl-impersonate/tests/signatures/*.yaml` секции `http3` **нет ни в одном
файле** — при том что README корпуса её описывает. H3-данные живут в C-структурах
`patches/curl.patch` и только для четырёх целей: `chrome145`, `chrome146`,
`chrome150`, `firefox147`. У Safari и Tor их нет вовсе.

Значит импортёр этапа 3 эти поля заполнить не может, и профили H3 придётся
снимать самим либо переносить вручную из четырёх известных строк.
