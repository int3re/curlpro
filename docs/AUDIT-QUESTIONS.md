## Как работать с этим проектом

1. **Проверять замером, а не рассуждением.** Утверждение «этот порядок
   заголовков неверен» без прогона против стенда — гипотеза. Команды в
   разделе 5 брифинга.
2. **Сверяться с разделом 4 брифинга** перед тем, как назвать что-то багом:
   там перечислено то, что выглядит ошибкой, но сделано намеренно и проверено.
3. **Репозиторий открыт:** github.com/int3re/curlpro, лицензия Apache 2.0.
   В старых записях встречается ограничение «репозиторий локальный» — оно снято.
4. **Язык кода — английский**, язык документации — русский. По-английски пишутся
   комментарии, строки документации, сообщения ошибок и вывод утилит: библиотека
   открытая, и её читают не только по-русски. Документация проекта (README.md,
   ROADMAP.md, docs/) остаётся русской. У README и брифинга аудита есть
   полноценные английские двойники — README.en.md (606 строк против 593)
   и docs/AUDIT-BRIEF.en.md; это переводы, а не выжимки, и их совпадение
   по структуре проверяется тестом.

   Комментарии объясняют «почему», а не «что»: если правка отменяет чьё-то
   решение, стоит объяснить, чем прежнее рассуждение было неверным.
5. Читать `docs/STAGE*-RESULTS.md` выборочно — это хронология, лучший источник
   контекста «почему так», но целиком не нужна.

## Часть 2. Где нужна помощь

Задачи, в которых собственного решения пока нет. Упорядочены по ценности.

### 2.1 Порядок заголовков в HTTP/3 ✅ закрыто 2026-09-05

Между сборкой заголовков и проводом лежит HPACK/QPACK, и наблюдать нужно
именно провод. Состояние по транспортам:

| Транспорт | Чем проверяется |
|---|---|
| HTTP/1.1 | свой стенд `python/tests/rawserver.py` — публичные оракулы имена нормализуют, поэтому пришлось поднимать своё |
| HTTP/2 | `echo-server` отдаёт HEADERS-кадр в порядке провода (`/json/detail` → `detail.metadata.HTTP2Frames.Headers`); используется в `python/tests/test_h2_headers.py` |
| HTTP/3 | свой стенд `internal/client/h3stand_test.go` — QUIC на `uquic`, HEADERS разбирается своим `internal/qpack` |

Пробел по HTTP/2 был закрыт по ходу подготовки этого документа: стенд умел
отдавать порядок, но мы им не пользовались. Именно из-за этого прожил
незамеченным реальный баг — якорь пользовательских заголовков работал **только
на HTTP/1.1**, потому что все Python-тесты заголовков гоняют с
`force_http1=True` (см. `docs/STAGE13-RESULTS.md`).

**HTTP/3 закрыт тем же способом, что предлагался в вопросе** — своим сервером на
`uquic`, а не разбором pcap. Разбор HEADERS идёт через тот же `internal/qpack`,
которым `cmd/hcapture` снимает живой браузер, поэтому тест проверяет ровно то,
что показал бы захват. Четыре теста в `internal/client/h3order_test.go`: стенд
видит запрос, порядок на проводе совпадает с профилем, кастомный заголовок
встаёт перед служебным хвостом, переопределение профильного заголовка не
двигает имя.

Замер, порядок на проводе (Chrome 151, HTTP/3):

```
sec-ch-ua sec-ch-ua-mobile sec-ch-ua-platform upgrade-insecure-requests
user-agent accept sec-fetch-site sec-fetch-mode sec-fetch-user sec-fetch-dest
accept-encoding accept-language priority
```

С одним своим заголовком видно и переключение на набор fetch:

```
sec-ch-ua-platform user-agent sec-ch-ua x-custom-token sec-ch-ua-mobile accept
sec-fetch-site sec-fetch-mode sec-fetch-dest accept-encoding accept-language priority
```

Осталось ручным: сверка с **живым браузером** по HTTP/3 — она снимает эталон,
а не проверяет нас, и делается через `cmd/hcapture -auto -h3`.

### 2.2 Конкурентность ✅ закрыто 2026-09-05

Было: покрытие только через Python, где race detector не работает в принципе,
хотя в пуле уже находили нетривиальное — HTTP/1.1 портил открытый поток
параллельным запросом, потому что мьютекс отпускался до чтения тела
(`docs/STAGE12-RESULTS.md`).

Стало: `internal/client/concurrency_test.go` — восемь тестов под `-race`.

| Тест | Что держит |
|---|---|
| `TestConcurrentRequestsOneSession` | 12 горутин × 15 запросов, HTTP/1.1 и HTTP/2: каждый ответ соответствует своему запросу |
| `TestConcurrentStreamsAndRequests` | 8 открытых потоков и 80 обычных запросов вперемешку — тот самый сценарий STAGE12 |
| `TestConcurrentCloseDuringRequests` | закрытие сессии под нагрузкой: без зависаний, после закрытия код ошибки `session_closed`, второй `Close` не падает |
| `TestConcurrentPoolStaysWithinLimit` | 20 одновременных запросов держат в пуле ровно 6 соединений — `maxConnsPerHost` |
| `TestConcurrentOrphanIsUnregistered` | мягко вытесненное HTTP/2-соединение доигрывает потоки и уходит из `s.orphans` |
| `TestConcurrentCookieWrites` | 80 параллельных записей в банку и чтения вперемешку — все 80 записей на месте |
| `TestConcurrentStreamCloseRacesSessionClose` | закрытие потока и закрытие сессии одновременно, пять попыток |
| `TestConcurrentContextCancelDuringRequest` | десять отменённых запросов не оставляют соединение занятым |

**Что нашли:** гонку в зависимости — она в таблице долгов выше. Своего кода
детектор не поймал ни на одном из восьми.

Команда: `CGO_ENABLED=1 CC=D:/mingw64/bin/gcc.exe go test -race ./internal/...`
(на Windows детектору нужен gcc из MinGW).

### 2.3 Утечки на границе FFI ✅ закрыто 2026-09-05

Было: 33 экспорта (в прежней записи стояло 19), у каждого своя дисциплина
владения. Уже наступали на то, что `restype` обязан быть `c_void_p`, а не
`c_char_p`, иначе ctypes теряет указатель и `curlpro_free` не вызывается.

Стало: экспорт `curlpro_debug_counts` отдаёт размеры всех реестров — сессии,
потоки, сокеты, вызовы в полёте — плюс число горутин и кучу. Утечка хендла
невидима из Python: объект уничтожен, а Go держит соединение и горутину.

Сплошная проверка границы прошла и ничего не нашла:

| Что проверялось | Результат |
|---|---|
| 5000 запросов, 200 сессий, 300 потоков | RSS 43.9 → 57 МБ и дальше ровно, куча 2576 → 3958 КБ |
| Горутины | было 1, стало 1 |
| Сессии, потоки, сокеты | реестры возвращаются к исходному размеру |
| Поток брошен без `close()` | освобождается через `__del__` |
| Исключение между `open` и `close` | хендл не остаётся |
| Отменённые асинхронные вызовы | `pending` возвращается к нулю |
| Обращения к несуществующим хендлам | ошибка, реестр не растёт |
| `curlpro_session_close` во время `curlpro_stream_read` | три прогона: без зависания и падения, чтение доходит до конца |

Закреплено регрессией: `python/tests/test_ffi_registry.py` (10 тестов).

Осталось известным свойством, а не долгом: хендлы, созданные из сессии, не
освобождаются `curlpro_session_close` — их держит Python до `__del__`. Замер:
`streams: 10` пока объекты живы, `0` после освобождения.

### 2.4 Как замерить `Content-Length` и `custom_anchor`

Обе позиции сейчас — догадки, потому что готовые сигнатуры `curl-impersonate`
сняты с GET-запросов, где `Content-Length` отсутствует, а пользовательских
заголовков нет вовсе.

**Нужно:** способ снять POST от живого Chrome/Firefox/Safari с
пользовательским заголовком — желательно воспроизводимо, а не разово руками.
Схема захвата описана в `docs/CAPTURE.md` (echo-server +
`--host-resolver-rules`), но она заточена под навигационный GET.

### 2.5 Слабое место схемы профилей ✅ отвечено в STAGE15

Профиль — это данные, но не всякий браузер data-only: новый тип TLS-расширения
требует Go-кода (`TLSExtension` с `UnmarshalJSON`), ECH и QUIC transport
parameters — пост-процессоров, потому что upstream uTLS их из JSON не грузит.

**Вопрос:** можно ли сузить эту границу? Например, обобщённое расширение
«неизвестный тип + сырые байты», чтобы новый кодпоинт не требовал релиза.
Риск: молча отправить мусор вместо осмысленного расширения.

### 2.6 Производительность

Замерялось один раз: 1775 req/s против 1352 у `curl_cffi` на локальном стенде
(`docs/STAGE5-RESULTS.md`). Тела ходят бинарным кадром, JSON — только метаданные.

**Вопрос:** где остались очевидные резервы. Подозрительные места — сборка
заголовков на каждый запрос (несколько аллокаций карт и слайсов),
пересоздание `ClientHelloSpec` на каждое соединение (обязательное, см.
инварианты — но можно ли удешевить), путь `bridge.go` между `net/http` и `fhttp`.

## Часть 3. На что посмотреть свежим взглядом

Здесь конкретных подозрений нет — интересен именно незамыленный разбор.

- **`internal/client/headers.go`** — самый плотный по смыслу файл: слоты,
  якорь, регистр, взаимодействие с сортировщиком `fhttp`. Недавно переписан,
  и переписывание вскрыло три бага (`docs/STAGE13-RESULTS.md`). Логика
  общая для трёх транспортов — цена ошибки высокая.
- **`internal/client/retry.go` + `stream.go`** — повторы, дренаж тела,
  идемпотентность, `Retry-After`. Взаимодействие с редиректами и общим
  дедлайном нетривиально.
- **`internal/client/websocket.go`** (359 строк) — самый крупный файл клиента.
  Маскирование по RFC 6455, фрагментация, close-handshake. Уже ловили, что
  WebSocket мутировал `s.opts.ForceHTTP1` и тем менял ALPN всей сессии.
- **`internal/profile/build.go`** — 22 типа расширений, собираются из JSON.
  Ошибка здесь тихо портит отпечаток, а не падает.
- **`internal/h3/`** — вендор с точечными правками; интересны `fingerprint.go`,
  `order.go`, `request_writer.go`. Остальное — апстрим, трогать смысла мало.
- **Схема профиля против реальности** — `docs/PROFILE-SCHEMA.md` и любой файл
  из `profiles/`. Нет ли полей, которые объявлены, но не влияют ни на что?
