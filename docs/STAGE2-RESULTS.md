## Разведка JSON-кодека uTLS

Перед проектированием формата проверил эмпирически, что кодек реально умеет:

| Факт | Следствие для схемы |
|---|---|
| **17 из 18** расширений Chrome 151 реализуют `UnmarshalJSON` | декларативный путь возможен |
| ECH (`GREASEEncryptedClientHelloExtension`) — **не реализует** | нужен пост-процессор |
| ECH не грузится **ни по имени, ни по кодпоинту**: `extension name is unknown to the dictionary` | ECH отсутствует и в словаре `dicttls` |
| `ClientHelloSpec` **не имеет `MarshalJSON`** | сериализацию спеки пришлось бы писать самому |
| `application_settings_new` (ALPS 17613) грузится штатно | новый кодпоинт Chrome поддержан |

Последний пункт определил дизайн: раз обратной сериализации нет, базовый профиль
хранит **захваченные байты** (`raw_client_hello`), а версии поверх описываются
декларативными оверрайдами. Это ровно тот случай, ради которого схема и нужна:
месячный бамп Chrome меняет User-Agent, `sec-ch-ua` и иногда sigalgs.

## Устройство

`internal/profile`:
- `profile.go` — типы, реестр, разрешение `based_on` с защитой от циклов
  и ограничением глубины
- `spec.go` — сборка `ClientHelloSpec`, пост-процессор ECH, применение оверрайдов

Два источника ClientHello, взаимоисключающие:
- `raw_client_hello` — base64 живого захвата, точный путь
- `client_hello_spec` — декларативный JSON uTLS, редактируемый руками

**Пост-процессор ECH** вырезает `{"name":"encrypted_client_hello"}` из JSON до
передачи в uTLS, запоминая позиции, и вставляет `utls.BoringGREASEECH()` обратно
на те же индексы. Тест `TestSpecFromJSONHandlesECH` сначала проверяет, что голый
`json.Unmarshal` действительно падает, — если однажды uTLS научится грузить ECH,
тест упадёт и напомнит упростить код.

## Принцип: ломаться громко

`DisallowUnknownFields` при разборе профиля, ошибка на оверрайд, которому не
нашлось расширения, ошибка на цикл и на обрыв цепочки `based_on`.

Это прямая реакция на то, как ведёт себя curl-impersonate: нестандартный порядок
TLS 1.3-шифров там молча заменяется на `kCiphersAESHardware` — ни ошибки, ни
предупреждения, просто чужой отпечаток. Тихая деградация в задаче про отпечатки
хуже отказа.

## Исправленный дефект захвата

Все шесть сэмплов этапа 0 содержали заголовки `/favicon.ico`, а не основного
запроса. Причина: по одному h2-соединению браузер шлёт навигацию и следом favicon,
обе дают detail-запись, а разбор оставлял последнюю.

Это исказило бы профиль: у favicon нет `upgrade-insecure-requests`, другие
`sec-fetch-*` и другой `accept`. Исправлено в `analyze.py` — detail накапливаются,
нужный выбирается по `:path` (флаг `--path`).

Побочно подтвердился разбор PRIORITY из этапа 0: после фильтрации favicon
осталась одна запись `1:1:0:256` вместо двух — второй стрим действительно был favicon.

Полученный порядок из 13 заголовков совпал с тем, что записан в корпусе
curl-impersonate для Chrome 150, — независимое подтверждение корректности.
