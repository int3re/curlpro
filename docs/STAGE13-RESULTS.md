# Этап 13 — слоты заголовков и общий построитель (фазы E, E-3)

Дата: 2026-09-02.

Порядок заголовков — такая же часть отпечатка, как набор шифров, но до этого
этапа он проверялся только через сеть и только на HTTP/1.1. Из-за этого три
дефекта жили незамеченными.

## Слот вместо приписки в конец

Раньше `cookie` и любой пользовательский заголовок дописывались в конец
собранного списка. Для cookie это неверно всегда: Chrome шлёт его между
`accept-language` и `priority`, то есть отпечаток ломался даже без единого
пользовательского заголовка — достаточно было включить jar.

Теперь профиль объявляет `cookie` **пустым слотом** — позиция без значения:

```json
{ "key": "cookie", "value": "" }
```

Пустой слот задаёт место; если jar пуст, заголовок в запрос не попадает
(`TestEmptyCookieSlotDisappears`). Слот добавлен во все 44 профиля, в
`headers.order` и в `http1.order`.

Для пользовательских заголовков введён якорь — `headers.custom_anchor`:

```json
{ "custom_anchor": "accept-encoding" }
```

Имена, которых в профиле нет, вставляются **перед** якорем. Служебный хвост
(`accept-encoding`, `cookie`, `priority`) браузер дописывает последним, поэтому
заголовок после него — заметная аномалия.

Проверено на стенде: `... Sec-Fetch-Dest X-Custom Accept-Encoding
Accept-Language cookie priority`.

## Дубликаты ключей

Профиль писал `user-agent`, пользователь передавал `User-Agent` — в карте
оказывалось два ключа при одном имени в порядке. HTTP/1.1 выдавал две строки,
HTTP/2 — недетерминированный порядок, потому что сортировщик считает такие
ключи равными. Воспроизводилось и без пользователя: профиль кладёт
`Sec-Fetch-Site`, редирект — `sec-fetch-site`.

Введена карта слотов по имени в нижнем регистре. Переопределение меняет
значение **на прежнем месте**, а не переносит заголовок в конец.

## Три бага, которые нашлись при объединении

`applyHeaders` (fhttp) и `applyH3Headers` (net/http) были двумя копиями одних
правил и успели разойтись. Обе сведены к общему `buildHeaders`, а пути
различаются только записью в свой тип Header. Что вскрылось:

**1. Якорь работал только на HTTP/1.1.** `reorder` вызывался, лишь когда задан
явный порядок, а он есть только у `http1.order`. В HTTP/2 и HTTP/3 — основных
путях — кастомный заголовок уходил в самый конец, после `priority`. Python-тесты
этого не видели: все гоняют с `force_http1=True`. Поймано Go-тестом
`TestCustomHeaderGoesBeforeAnchor`. Исправлено добавлением порядка профиля в
цепочку `firstNonEmpty`.

**2. HTTP/3 терял `SuppressHeaders`.** После редиректа `sec-fetch-user` обязан
исчезнуть — на пути HTTP/3 он оставался.

**3. HTTP/3 игнорировал слот cookie** и дописывал его в конец.

## Порядок как желаемый, а не фактический

`Content-Length` добавляет сам транспорт — `transfer.go:addHeaders`, уже после
сборки заголовков. Его не было в списке порядка, поэтому он уходил в хвост,
тогда как браузер шлёт его сразу за `Connection`.

Ключ порядка теперь передаёт **желаемый** список, включая имена, которых в
запросе ещё нет: `wireOrder`. Имя без заголовка сортировщик просто не встретит
(`headerSorter.Less` ищет по карте), поэтому лишние места безвредны.

Проверено сквозным тестом через настоящий `Request.Write`
(`TestContentLengthTakesItsSlot`): при слоте в профиле заголовок встаёт третьим.

⚠ **Слот `Content-Length` в профили не добавлен.** Механизм готов и проверен, но
точная позиция требует замера: готовые сигнатуры curl-impersonate сняты с GET,
где заголовка нет вовсе. Внесение в 44 профиля «по общему знанию» противоречит
смыслу проекта. См. открытые вопросы.

## Прогоны шли на устаревшей библиотеке

Часть проверок этого этапа была недостоверна. `_ffi.py` ищет `curlpro.dll` в
`python/curlpro/lib/` и `dist/`, а сборка велась вручную в
`python/curlpro/_curlpro.dll` — путь, который не используется никем. Python
грузил DLL получасовой давности, и «95 passed» относилось не к тому коду.

Файл удалён; сборка только через `.\build.ps1`, которая кладёт в `dist/`.
После пересборки все проверки повторены — результаты ниже относятся к
актуальному коду.

Чтобы это не повторилось, введена сверка версий (первый пункт фазы F).
`curlpro_version` поднят до `0.2.0`, `_ffi.py` держит `REQUIRED_VERSION` и при
загрузке отказывается работать со старой библиотекой:

```
библиотека версии 0.1.0 старее требуемой 0.2.x — часть опций она молча
проигнорирует. Пересоберите: .\build.ps1 (кладёт в dist/)
```

Молчание было главной проблемой: `DisallowUnknownFields` нигде не включён, обе
стороны переживают незнакомые поля, поэтому старая DLL просто не видела новых
опций — `follow_redirects=False` не действовал, и это выглядело ошибкой логики.
Отсутствующий экспорт теперь тоже даёт внятное сообщение вместо
`AttributeError` при импорте пакета.

## Плавающий JA4 у двух профилей — это норма

`chrome-119-linux` и `edge-120-linux` дают то 16, то 17 расширений
(`t13d1516h2…` / `t13d1517h2…`). Причина: GREASE ECH в uTLS выбирает длину
payload случайно из `{128, 160, 192, 224}` (`u_ech.go:304`), длина ClientHello
скачет на 32–96 байт, и `BoringPaddingStyle` то добавляет `padding`, то нет.

Так же ведёт себя BoringSSL в Chrome, поэтому это не дефект, а корректная
эмуляция — и ровно ради таких случаев baseline хранит **набор** значений JA4,
а не одно. Оба варианта записаны в эталон.

## Открытые вопросы

- **Позиция `Content-Length`** в `http1.order` и `headers.order` — нужен захват
  POST-запроса с живого Chrome/Firefox/Safari. Механизм готов, недостают данные.
- **`custom_anchor: "accept-encoding"`** проставлен во все профили как
  умолчание из плана и тоже не подтверждён замером. Позиция правдоподобна
  (служебный хвост идёт последним), но это догадка.
- Порядок при POST в HTTP/2 не проверен вовсе: стенд возвращает только
  Akamai-отпечаток и порядок псевдо-заголовков, а обычные — нет.
