# Этап 10 — повторы, переопределения на запрос, заголовки сессии

Дата: 2026-09-01.

## Что добавлено

```python
# Повторы: по умолчанию только идемпотентные методы
with curlpro.Session(retries=3, respect_retry_after=True) as s:
    s.get(url)                       # 503 → пауза → повтор
    s.post(url, retry_methods=["POST"])   # повтор POST — осознанный выбор

# Переопределения на один запрос
s.get(url, timeout=2.0)
s.get(url, allow_redirects=False)
s.get(url, proxy=False)              # в обход прокси сессии
s.get(url, proxy="socks5://other:1080")

# Заголовки сессии
s.headers["X-Api-Key"] = "secret"    # во всех последующих запросах
del s.headers["X-Api-Key"]
s.headers.clear()                    # остаются только профильные
```

## Два бага, найденных проектированием

Перед реализацией дизайн прогнан через параллельный анализ с рецензентами.
Он вскрыл две поломки в уже написанном коде — обе тихие.

### Редирект терял половину запроса

`nextRequest` собирал новый запрос перечислением полей. Не копировались
`BodyFile`, `BodySize`, `Multipart`, `Timeout`, `MaxRedirects`, `Proxy`, `Retry`.

Следствие: **307 с файлом уходил на сервер с пустым телом**. Сервер отвечал 200
на пустой POST — хуже, чем ошибка, потому что клиент считал операцию успешной.
Второе следствие: per-request таймаут действовал только на первый шаг цепочки.

Исправлено копированием структуры целиком (`next := *prev`) с последующим
изменением того, что обязано меняться. Ручной перечень полей терял бы и следующее
добавленное поле — так же тихо.

### Таймаут отсчитывался заново на каждом шаге

`send` создавал `context.WithTimeout` внутри себя, поэтому двадцать редиректов
давали двадцать таймаутов вместо одного. Проверка `time.Now().After(deadline)`
между шагами ограничивала лишь момент старта, а не длительность.

Исправлено передачей общего дедлайна: `context.WithDeadline` вместо
`WithTimeout`. Проверено тестом — цепочка из четырёх редиректов с задержкой
обрывается за 1.5 с при пределе 1.5 с, а не за 6 с.

### Заодно

- `timeout=0` означал разное: на сессии подставлял 30 секунд, на запросе давал
  мгновенный таймаут. Теперь отвергается с объяснением.
- `sec-fetch-user` после редиректа удалялся из `Headers`, хотя приходит
  из профиля — то есть не удалялся вовсе. Появилось поле `SuppressHeaders`,
  гасящее заголовок после сборки.
- Зачистка `authorization` при переходе на другой хост перечисляла два
  написания и пропустила бы `AUTHORIZATION`. Теперь регистронезависимо.
- `sameHost` сравнивал только имя хоста: переход на другой порт считался
  тем же источником. Заменено на сравнение схемы, хоста и порта.

## Решения, принятые в реализации

**Повторяются только идемпотентные методы.** Повтор POST может создать второй
заказ: сервер мог обработать запрос и не успеть ответить, и клиент этого
не различает. Разрешение — явным списком `retry_methods`.

**Экспоненциальная задержка с джиттером.** Без него все клиенты, получившие 503
одновременно, повторят тоже одновременно и добьют сервер. `Retry-After`
имеет приоритет над формулой: сервер, который просит подождать, знает лучше.

**Прокси входит в ключ пула соединений.** Иначе запрос «в обход прокси» получил
бы соединение, уже поднятое через прокси, и переопределение молча не сработало бы.

**Три состояния прокси, а не два.** `None` — наследовать сессионный, `False` —
идти напрямую, строка — использовать указанный. Одной строкой это не выразить:
пустая строка уже занята под «напрямую».

**Кастомный заголовок уходит в конец, но переопределение профильного сохраняет
позицию.** Перенос `User-Agent` в конец сломал бы отпечаток; проверяется тестом
на сыром сервере.

## Проверка

**88 тестов Python** (было 66), 14 Go, все 44 профиля проходят валидацию.

Новый набор `test_session_features.py` — 22 теста, включая:
- ровно три попытки при сценарии `503, 503, 200`;
- POST не повторяется без разрешения (счётчик на сервере равен единице);
- тело в 4 КБ переживает 307 и отбрасывается на 303;
- `proxy=False` не увеличивает счётчик туннелей прокси;
- переопределение `User-Agent` не двигает его позицию.

Тестовый стенд `flakyserver.py` задаёт сценарии ответов и считает попытки:
публичные сервисы не дают отличить «клиент повторил» от «сходил один раз».
