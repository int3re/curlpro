# curlPro — полное руководство

*[English version](GUIDE.md)*

Вся библиотека в одном документе, для двух читателей: человека, который её
встраивает, и ИИ-ассистента, который изучает её перед тем, как трогать код.
Каждое число и каждое поведение здесь сверены с кодом 22 сентября 2026 года,
на версии 0.12.0. Где README говорит меньше, этот документ говорит больше; где
они расходятся, ошибается этот документ, и его надо поправить — скажите об этом.

Ассистенту, читающему это: библиотека уже делает почти всё, что скрапер пишет
руками. Раздел 15 перечисляет, что не нужно переписывать. Раздел 16 — какие
утверждения проверены и какие оказались ложью.

## 1. Что это, в трёх предложениях

curlPro — HTTP-клиент для Python, чей трафик несёт сетевой отпечаток браузера:
TLS ClientHello, кадры HTTP/2 и HTTP/3, набор, порядок и регистр заголовков,
рукопожатие WebSocket, даже границу multipart. Браузер описан JSON-профилем, а
не кодом, поэтому новая версия браузера — правка данных, доступная любому
пользователю прямо во время работы. Python-пакет — тонкий слой `ctypes` над
Go-библиотекой (uTLS для TLS, пропатченный fhttp для HTTP/1.1 и HTTP/2,
вендоренный uquic для HTTP/3), которая едет внутри колеса.

Всем, что ниже, управляют четыре правила. Они объясняют почти всё, что на
первый взгляд удивляет:

- **Профили — данные.** Браузер — это `.json`-файл; код общий. Если у браузера
  что-то меняется, меняется профиль, а не библиотека.
- **Измерено, а не предположено.** Значение попадает в профиль только после
  того, как его видели на проводе у настоящего браузера. Где ничего не
  измерено, библиотека говорит об этом, а не угадывает.
- **Отказать, а не проигнорировать.** Опция, которую нельзя выполнить,
  поднимает ошибку с причиной. Ничего не понижается, не отбрасывается и не
  подменяется молча.
- **Правда — на проводе.** `session.fingerprint()` и `session.audit()`
  считаются по байтам, которые ушли бы наружу, а не по конфигурации.

## 2. Установка и запуск

```bash
pip install curlpro
```

Колесо несёт нативную библиотеку и все 56 профилей; ни Go, ни компилятор C не
нужны. Колёса есть для Linux x86-64 и ARM64 (glibc 2.28+), macOS 13+ на Intel
и Apple Silicon и Windows x64; Python 3.9 и новее. Всё остальное собирается из
исходного архива с Go и компилятором C (`README.md`, «Install»).

Профили попадают в библиотеку тремя путями:

- **Из колеса, сами.** `ensure_loaded()` срабатывает на первом `Session`;
  вызывать ничего не нужно.
- **Из каталога.** `curlpro.load_profiles("profiles")` — так нужно в
  чекауте репозитория, где профили лежат рядом с пакетом, а не внутри него.
- **Во время работы.** `curlpro.register_profile(dict_or_json)` добавляет один
  профиль без релиза.

У нативной библиотеки есть версия ABI (`0.22` в этом релизе), которую Python
проверяет при импорте. Колесо всегда несёт согласованную пару; проверка нужна
для сборок из исходников и для `CURLPRO_LIBRARY`, которая указывает пакету на
вашу собственную библиотеку. Несовпадение поднимает ошибку при импорте с
командой пересборки в тексте.

Из чекаута на Windows: `.\build.ps1` пишет `dist/curlpro.dll`, затем
`cd python; $env:PYTHONPATH='.'; python -m pytest tests`.

## 3. Ментальная модель

Три слоя, каждый добавляет к нижнему:

| Слой | Владеет | Где задаётся |
|---|---|---|
| Профиль | отпечаток: TLS, HTTP/2, HTTP/3, наборы заголовков и их порядок, рукопожатие WebSocket, устройства | `profiles/*.json`, `register_profile()` |
| Сессия | память и политика: куки, добавленные заголовки, убранные заголовки, прокси, таймауты, ретраи, редиректы, устройство, режим | `curlpro.Session(...)` |
| Запрос | один обмен: тело, params, заголовки, порядок, протокол и любое переопределение политики сессии | `s.get(...)`, `s.request(...)` |

Запрос собирается так: заголовки профиля для выбранного набора (навигация или
fetch), потом заголовки сессии, потом заголовки запроса, потом шаблон порядка,
потом удаления. Результат — то, что показывает `fingerprint().headers`. Одна и
та же сборка обслуживает HTTP/1.1, HTTP/2 и HTTP/3 — правила существуют в
одном экземпляре.

## 4. Сессии: каждый параметр

`curlpro.Session(impersonate="chrome-151-windows", **options)`. У каждой опции
значение по умолчанию воспроизводит браузер; таблица говорит, что меняется,
когда вы её трогаете.

| Параметр | По умолчанию | Значение |
|---|---|---|
| `impersonate` | `chrome-151-windows` | имя профиля; `list_profiles()` знает все 302, `list_profiles(measured=True)` — 42 снятых целиком |
| `verify` | `True` | `True` — системные корни; путь к PEM — доверять только ему; `False` — без проверки |
| `cert` | `None` | пути `(certificate, key)` для mTLS |
| `trust_env` | `True` | брать прокси из `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY`, учитывая `NO_PROXY`; явный `proxy` всегда сильнее |
| `timeout` | `30.0` | предел на **весь** запрос, включая редиректы; пара `(connect, total)` отдельно ограничивает соединение. `float("inf")` — без предела |
| `connect_timeout` | `None` | предел на соединение по имени: резолв, TCP, TLS. Сильнее первого элемента пары |
| `response_timeout` | `None` | сколько ждать **заголовков** ответа после отправки запроса. Тело не ограничивает. Поднимает `Timeout` со словами «response headers» |
| `proxy` | `None` | `http://`, `https://`, `socks5://`, `socks5h://`, допустим `user:pass@`; голый `host:port` читается как `http://`. Первый CONNECT идёт без учётных данных и добавляет их после 407, как Chrome; прокси, который вместо этого рвёт соединение, получает второй CONNECT с ними на свежем соединении; тот, что рвёт и его, поднимает ошибку с кодом `proxy_closed` |
| `default_headers` | `True` | слать заголовки профиля. `False` шлёт только ваши — и вовсе без `User-Agent`, если вы его не передали; библиотека никогда не подставляет Go-шный |
| `header_order` | `None` | порядок отправки как шаблон с `...` вместо собственного порядка профиля; раздел 6 |
| `allow_redirects`, `max_redirects` | `True`, `20` | следовать 3xx; цепочка в `r.history` |
| `cookies` | `True` | банка, общая для запросов сессии |
| `force_http1` | `False` | предлагать в ALPN только `http/1.1`. Это меняет JA4 (два его символа), и законно: так выглядит браузер без h2 |
| `post_quantum` | `True` | `False` убирает X25519MLKEM768 и его key_share на 1216 байт: hello браузера с выключенным политикой постквантовым обменом. JA4 не меняется, JA3 и размер меняются, hello влезает в один TCP-сегмент |
| `resume` | `True` | возобновление TLS-сессии по билетам, кэш на сессию, как у браузера. Включено с тех пор, как возобновляющий hello измерен (Chrome 153 и Firefox 156): первый hello плюс `pre_shared_key` в конце, без early data, а у Firefox ещё и без `session_ticket` — это и уходит. Первый hello сессии не тронут, так что каждый отпечаток остаётся прежним |
| `http3` | `False` | идти в QUIC сразу. Профилю нужна секция `http3` (она есть у четырёх, раздел 12) |
| `alt_svc` | `True` | переходить на HTTP/3 после заголовка `Alt-Svc`, как браузер; неудачная попытка откатывается на TCP и не повторяется 5 минут, с удвоением до 24 часов. Нужна секция `http3`; через прокси не работает |
| `resolve` | `None` | `{"example.com:443": "10.0.0.7"}` — `--resolve` из curl; SNI и `Host` сохраняют имя. Через прокси не работает |
| `ip_version` | `None` | `"4"` или `"6"` — одно семейство адресов |
| `keep_alive` | `True` | переиспользовать соединения. `False` закрывает после каждого ответа, не посылая `Connection: close`. Простаивающее соединение, которое закрыл сервер, выбрасывается из пула, а запрос, чьё переиспользованное соединение умерло до первого байта ответа, уходит ещё раз по новому, при любом методе, как у Chromium (раздел 9) |
| `max_idle_conns`, `idle_conn_timeout` | `0`, `0.0` | размер пула и время жизни простаивающего соединения; ноль — умолчания библиотеки |
| `retries` | `0` | попытки после первой. Повторяются только идемпотентные методы, если `retry_methods` не скажет иначе |
| `retry_statuses` | 408, 429, 500, 502, 503, 504 | какие ответы считаются сбоем, который стоит повторить |
| `retry_methods` | идемпотентные | GET, HEAD, PUT, DELETE, OPTIONS, TRACE; явный список разрешает POST |
| `retry_backoff`, `retry_max_backoff` | `0.2`, `10.0` | секунды; экспонента между ними |
| `respect_retry_after` | `True` | заголовок `Retry-After` задаёт ожидание |
| `mode` | `"auto"` | набор заголовков: `navigate`, `fetch` или выбор по запросу (раздел 7) |
| `page` | `None` | страница, с которой делаются запросы, — инициатор. Выводит `Referer`, `Origin` и `sec-fetch-site` так, как их выводит браузер (раздел 7); `s.page = url` двигает её вместе со скрапером. Должен быть абсолютным http(s) URL |
| `credentials` | `"same-origin"` | режим credentials запросов в режиме fetch, словами `fetch()`: `same-origin` шлёт куки только на собственный origin страницы — умолчание `fetch()` и XHR, — `include` шлёт их всюду, где позволяют правила SameSite, `omit` не шлёт. Замерено на Chrome 153 и Firefox 156: обычный `fetch()` на другой origin *того же сайта* не несёт ни одной куки (раздел 10) |
| `samesite` | `True` | применять атрибут `SameSite` кук и правило третьей стороны семейства к запросам со страницы `page`; `False` шлёт всё, что подобрала банка, как до 0.10 (раздел 10) |
| `preflight` | `True` | слать CORS-preflight, который браузер шлёт перед непростым кросс-origin fetch, проверять ответ и хранить его на время `Access-Control-Max-Age`; отказ поднимает `CORSError`, и запрос не уходит. `False` шлёт сразу, как до 0.10 (раздел 7) |
| `device`, `devices` | `None` | личность для профиля с пулом — телефон на Android, выпуск Windows и сборка Chrome на десктопе, версия iOS на iPhone — имя из списка профиля или `"random"` — и свой список (раздел 11) |
| `max_response_size` | `None` | предел тела в байтах; превышение поднимает ошибку с кодом `too_large`. Не задан: 100 МиБ для буферизованного ответа (`DEFAULT_MAX_RESPONSE_SIZE`, с 0.12) и без предела для потока; задан — ограничивает оба, включая `read()` потока; `0` — без предела. `iter_content()` не ограничивается никогда |
| `hooks` | `None` | `{"request": [...], "response": [...], "error": [...]}`; раздел 9 |

Атрибуты сессии, которые стоит знать: `s.headers` (отображение добавленных вами
заголовков плюс `s.headers.suppressed`), `s.cookies` (раздел 10), `s.hooks`,
`s.impersonate`, `s.fingerprint(url="https://example.com/")`, `s.audit(mode=None)`,
`s.headers_for(...)`, `s.preflight_for(...)`,
`s.close()`. Сессия — контекстный менеджер; `__del__` тоже закрывает её.

## 5. Запросы: каждый параметр и ответ

`s.request(method, url, **kw)`, с сокращениями `get`, `post`, `put`, `patch`,
`delete`, `head`, `options`. Модульные `curlpro.get(url, impersonate=...)` и
собратья открывают сессию на один запрос. Всё, что задано на сессии, здесь можно
переопределить для одного запроса; `None` значит «как у сессии». С 0.12
глаголы типизированы: `**kw` — это `Unpack[curlpro.RequestKwargs]`, так что
mypy, pyright и редакторы проверяют каждое имя и тип, а обёртка может так же
аннотировать свой `**kw`.

| Параметр | Значение |
|---|---|
| `params` | строка запроса, отображение или пары, вливается в URL |
| `auth` | `("user", "password")` для Basic или строка как bearer-токен |
| `data` | тело как bytes или str |
| `json_body` | любое JSON-сериализуемое значение; ставит `content-type: application/json`, если вы не поставили |
| `fields` | форма; одна — `application/x-www-form-urlencoded`, с `files` — multipart |
| `files` | файлы multipart; граница генерируется в стиле профиля (`----WebKitFormBoundary…` у Chrome, дефисы у Firefox) |
| `body_file` | путь, который потоком идёт телом с явным `Content-Length`; браузер никогда не грузит файл chunked |
| `headers` | ваши заголовки. Значение `None` **убирает** заголовок, который послали бы профиль или сессия; `""` шлёт его пустым. Всё, кроме `str` и `None`, — `TypeError` с именем заголовка |
| `header_order` | шаблон порядка для этого запроса, сильнее сессионного (раздел 6) |
| `default_headers` | `True`/`False` — заголовки профиля, в обе стороны, для этого запроса |
| `session_headers` | `False` — без заголовков и удалений, заданных на сессии |
| `cookies` | `False` — не слать банку и не запоминать `Set-Cookie`; двусторонне намеренно |
| `protocol` | `"http1"`/`1.1`, `"h2"`/`2`, `"h3"`/`3`. `h2` оставляет полный список ALPN и **падает**, если сервер выбрал `http/1.1` (ни один браузер не предлагает h2 в одиночку); `h3` требует TLS; поверх `http://` оба отклоняются |
| `timeout`, `connect_timeout`, `response_timeout` | как на сессии, для этого запроса |
| `proxy` | адрес, либо `False` — напрямую, в обход прокси сессии |
| `allow_redirects`, `max_redirects`, `retries`, `retry_*`, `respect_retry_after` | переопределения политики сессии; `retries=0` выключает ретраи сессии для этого запроса |
| `mode` | `"navigate"` или `"fetch"`; `fetch` на профиле без набора fetch отклоняется с причиной |
| `page` | страница, с которой сделан этот запрос, поверх сессионной; `False` шлёт его вовсе без инициатора |
| `credentials` | `"same-origin"`, `"include"` или `"omit"` для этого запроса в режиме fetch (раздел 10) |
| `preflight` | `False` шлёт этот кросс-origin fetch без `OPTIONS`, который браузер шлёт первым; `True` шлёт его, когда того требует стандарт Fetch (раздел 7) |
| `expect` | `Expect(...)`; несовпадение поднимает `ExpectationFailed` (раздел 8) |
| `rollback_cookies` | `True` возвращает банку к состоянию до запроса, если запрос не удался, включая проваленное ожидание |

Ответ:

| Член | Значение |
|---|---|
| `status`, `ok`, `proto` | `200`, `status < 400`, `"HTTP/1.1"` / `"HTTP/2.0"` / `"HTTP/3.0"` |
| `headers` | `Headers`: `dict[str, list[str]]` всех значений всех заголовков, поиск в котором не учитывает регистр — `r.headers.get("retry-after")` находит `Retry-After`; `.first(name)` даёт первое значение строкой. До 0.12 — обычный dict, где `.get` в нижнем регистре возвращал `None` |
| `header(name)` | первое значение без учёта регистра или `None` |
| `content`, `text` | байты; str, декодированная найденной кодировкой |
| `encoding` | из `Content-Type`, потом BOM, потом `<meta charset>` в первых килобайтах; присваиваемо, когда сайт объявляет её неверно |
| `json()` | `json.loads` по сырым байтам — UTF-8/16/32 парсер узнаёт сам |
| `url` | конечный URL после редиректов |
| `history` | цепочка редиректов как записи `Redirect(status, url, location)` |
| `preflight`, `preflights` | CORS-preflight, предварявший запрос, — запись `Preflight(url, status, headers, cached)` или `None`; и все они вдоль цепочки редиректов. `cached` значит, что `OPTIONS` не уходил: прежний ответ ещё покрывал запрос. У `StreamResponse` и у ответа `AsyncSession` есть оба поля (и `history`) — у второго не было до 0.10.1 |
| `cookies` | куки, которые поставил **этот** ответ, как отображение |
| `elapsed` | секунды, измеренные в Python вокруг нативного вызова |
| `raise_for_status()` | поднимает `HTTPError` (с `.status` и `.response`) на 4xx/5xx; иначе возвращает ответ |

Тела приходят распакованными: `gzip`, `deflate` (zlib или сырой), `br` и
`zstd`, в любом порядке наложения, который использовал сервер. Распаковывать
самому нечего.

Редирект с `https://` на `http://` не выполняется: 3xx возвращается с его
`Location`, потому что переход отправил бы куки и учётные данные открытым
текстом. Сам открытый `http://` работает — с порядком и регистром заголовков
HTTP/1.1 из профиля, потому что это всё, что видит собеседник по plain HTTP.

## 6. Заголовки: набор, порядок, удаления

**Набор** приходит из профиля и зависит от режима (раздел 7). Ваши заголовки
ложатся сверху: имя, которое профиль уже шлёт, сохраняет позицию и берёт ваше
значение; новое имя встаёт туда, куда браузер поставил бы кастомный заголовок —
перед якорем профиля, а не в конец.

**Удаление** — это `None`: `headers={"Sec-Fetch-User": None}` для одного
запроса, `s.headers["Sec-Fetch-User"] = None` для каждого запроса сессии.
Остальной набор не трогается. `""` — значение, оно уходит пустым заголовком,
как шлёт его браузерный `fetch()`. Значение запроса сильнее удаления на
сессии; `del s.headers[name]` и `s.headers.clear()` снимают удаления так же,
как убирают значения; `s.headers.suppressed` их перечисляет.

**Порядок** — шаблон поверх порядка браузера, на сессии или на запросе. `...`
означает «здесь собственные заголовки профиля»:

```python
s.get(url, headers={"X-Api-Key": "k"},
      header_order=[..., "accept", "x-api-key", ...])   # сразу после Accept, остальное как есть
s.get(url, header_order=["x-api-key", ...])            # первым
s.get(url, header_order=[..., "x-api-key"])            # последним
s.get(url, header_order=[..., "accept-encoding", "accept-language", ...])   # два заголовка профиля местами
```

Правила: `...` может быть несколько, и не названный заголовок профиля остаётся
рядом с названным соседом, за которым идёт в профиле; список без `...` — это
список, а за ним остаток профиля; имена, которых в запросе нет, пропускаются,
так что один шаблон подходит всем запросам; имя дважды отклоняется; кастомный
заголовок, которого шаблон не называет, по-прежнему встаёт перед якорем.
Раскрытие идёт по порядку реально используемого транспорта — у HTTP/1.1 есть
`Host` и `Connection` и свой регистр, у HTTP/2 нет ни того, ни другого, —
поэтому `fingerprint().headers` и `headers_http1` показывают ровно то, что
уйдёт.

`default_headers=False` — грубый инструмент: он убирает весь набор профиля,
включая `User-Agent`, и порядок вместе с ним. С 0.7.0 он редко нужен; `None`
убирает один заголовок и сохраняет остальные.

## 7. Навигация и fetch

Браузер шлёт разные наборы заголовков при переходе на страницу и при `fetch()`
или XHR со страницы. У набора fetch `accept: */*`, `sec-fetch-mode: cors`,
`sec-fetch-dest: empty`, `Origin`, `Referer` и нет `upgrade-insecure-requests`
и `sec-fetch-user`. Каждый профиль Chromium, Firefox, Tor и Yandex несёт оба
набора, измеренные (Chrome 152 и Firefox 154 на сыром стенде); Safari и okhttp
несут только навигационный.

В `mode="auto"` (по умолчанию) решает сам запрос, и любое из этого значит
fetch:

- метод, отличный от GET, HEAD и POST;
- тело, которое не форма — JSON, XML;
- заголовок, которого навигационный набор не несёт никогда — любой кастомный
  `X-…`, `Authorization`;
- значение fetch-метаданных, которого у навигации не бывает:
  `sec-fetch-mode: cors`, `sec-fetch-dest: empty`.

Поэтому `s.get(url, headers={"X-Api-Key": "k"})` уходит как fetch — так делает
браузер с кастомным заголовком. Когда вам это не подходит, скажите
`mode="navigate"`. Явный `mode="fetch"` на профиле без набора fetch отклоняется
с причиной: навигационный набор под именем fetch — `sec-fetch-user: ?1` рядом с
`sec-fetch-mode: cors` — запрос, которого не делает ни один браузер, и антибот
читает эту пару даром.

**Страница, с которой сделан запрос.** Браузерный fetch всегда идёт со
страницы, и три заголовка говорят, с какой: `Referer`, `Origin` и
`sec-fetch-site`. Без страницы уходят собственные значения профиля — переход по
набранному адресу (`sec-fetch-site: none`, без Referer) и fetch с собственного
origin запроса. Назовите страницу, на сессии или на запросе, и все три
выводятся так, как их выводят Chrome 153 и Firefox 156 (замер на
`cmd/hcapture -origins`, где оба сошлись в каждом значении):

```python
r = s.get("https://example.com/app")                 # переход: none, без Referer
s.page = r.url                                       # дальше — с этой страницы
s.post("https://api.example.com/v1/x", json_body=...)
# origin: https://example.com   referer: https://example.com/   sec-fetch-site: cross-site
s.get("https://example.com/next", page=False)        # один запрос без инициатора
```

| Заголовок | Правило (политика по умолчанию `strict-origin-when-cross-origin`) |
|---|---|
| `Referer` | URL страницы без фрагмента и учётных данных — на её собственный origin; origin страницы со слэшем — на любой другой; ничего с https-страницы на http-адрес |
| `Origin` | origin страницы — на каждом кросс-origin fetch, с телом и без, и на любом запросе с телом, включая отправку формы; same-origin GET fetch его не несёт |
| `sec-fetch-site` | `same-origin`, `same-site` (один регистрируемый домен по списку публичных суффиксов) или `cross-site`; вдоль цепочки редиректов — отношение страницы к каждому URL цепочки, и оно только ухудшается |

Переход со страницы считается кликом: `sec-fetch-user: ?1` остаётся. Referer
встаёт туда, куда его ставит семейство, — после `sec-fetch-dest` у Chromium,
после `Origin` у Firefox, — через слот в каждом профиле. Ваш собственный
`Referer`, `Origin` или `sec-fetch-site` сильнее выведенного.

Вдоль цепочки редиректов `Origin` называет origin, с которого цепочка началась,
— никогда не хост, на который перенёс запрос прыжок, — и становится `null` по
правилу стандарта Fetch: прыжок на другой origin с URL, с которым origin
запроса не совпадал. Поэтому fetch со страницы на чужой origin, отправленный
дальше ещё куда-то, приходит с `Origin: null`, а fetch на собственный origin
страницы, отправленный дальше, сохраняет origin страницы; Chrome 153 и
Firefox 156 согласны. Один Chromium ставит `null` ещё и на навигации с телом
(отправка формы с ответом 307) после любого кросс-origin прыжка, и профили
Chromium делают так же.

**Куки со страницы** следуют режиму credentials из `fetch()` и атрибуту
`SameSite` кук — раздел 10.

**CORS-preflight.** Браузер шлёт `OPTIONS` перед кросс-origin fetch, который не
«простой», — метод не из GET/HEAD/POST или заголовок вне CORS-safelist
(`Accept`, `Accept-Language`, `Content-Language`, `Content-Type` с формовым
типом; так что `application/json` считается, как и любой `X-…` или
`Authorization`), — и шлёт сам запрос, только если ответ его разрешает.
Библиотека делает то же, на каждом прыжке цепочки редиректов, с `OPTIONS`,
снятым на Chrome 153 и Firefox 156: `accept: */*`,
`access-control-request-method`, `access-control-request-headers` (имена,
строчные, отсортированные, через запятую), `origin`, собственные fetch-значения
профиля в preflight-порядке семейства — и ни кук, ни client hints, ни
собственных заголовков запроса. Ответ проверяется — 2xx,
`Access-Control-Allow-Origin` равен origin или `*` (не `*` при
`credentials="include"`, которому нужен ещё `Access-Control-Allow-Credentials:
true`), метод и каждый заголовок разрешены — и хранится на
`Access-Control-Max-Age` (пять секунд без заголовка, потолок два часа у Chromium
и сутки у Firefox), так что следующий запрос идёт без него, как в браузере.
Отказ поднимает `CORSError` с ответом (`.status`, `.headers`, `.reason`), и
запрос не уходит: сайт, работающий в браузере, отвечает на браузерный
preflight, так что отказ говорит, что `page` — не та страница, которую сайт
разрешает, либо что preflight отличается от браузерного, и это баг, о котором
стоит сообщить. `r.preflight` показывает, что ушло;
`s.preflight_for(method, url, headers=..., page=...)` показывает это до
отправки, `None` — когда браузер не послал бы ничего; `preflight=False` на
сессии или запросе шлёт сразу. Рукописный `s.options(url, headers={...})`
остаётся тем, что написано, — `OPTIONS` с этими заголовками, чего браузерный
preflight не делает никогда.

## 8. Ожидания и откат кук

```python
from curlpro import Expect

r = s.get(url, expect=Expect(status=200, body="Dashboard", not_body="captcha",
                             non_empty=True, encoding="utf-8"))
```

| Поле | Проверяет |
|---|---|
| `status`, `not_status` | код; несколько значений — «один из» |
| `body`, `not_body` | подстроки в теле; несколько — «все» |
| `headers`, `not_headers` | подстроки среди строк `name: value`, без учёта регистра |
| `non_empty` | тело не пустое |
| `json` | тело разбирается как JSON |
| `encoding` | найденная кодировка — эта; `cp1251` и `windows-1251` равны |

Несовпадение поднимает `ExpectationFailed` (код `expectation`), это
`CurlProError` с приложенным ответом. Проверка идёт после хуков ответа, по тому,
что они вернули.

`rollback_cookies=True` на запросе или `with s.cookies.transaction():` вокруг
нескольких возвращает банку, если блок поднял исключение — полузавершённый
логин хуже, чем никакого. Откат происходит до хуков ошибки, так что хук,
идущий в сеть, видит банку такой, какой она была. С 0.12 откат запроса точен:
нативная часть записывает, какие записи запрос изменил и что каждая заменила,
сама откатывает их, если запрос упал (и отменённый асинхронный тоже), а ответ,
не прошедший ожидание, откатывается по журналу, который он несёт, — куки,
полученные тем временем запросами других потоков, не трогаются. Раньше банка
очищалась и загружалась из снимка, и они стирались. `transaction()` по-прежнему
восстанавливает сделанный снимок, что годится для одного потока.

## 9. Ошибки и хуки

```python
try:
    r = s.get(url)
    r.raise_for_status()
except curlpro.Timeout:                  # код "timeout"
    ...
except curlpro.ExpectationFailed as e:   # код "expectation", e.response сохранён
    ...
except curlpro.HTTPError as e:           # из raise_for_status(): e.status, e.response
    ...
except curlpro.WebSocketClosed:          # код "ws_closed"
    ...
except curlpro.CurlProError as e:        # всё остальное: e.code, str(e)
    ...
```

`CurlProError` — это `RuntimeError`; всё остальное здесь наследуется от него.
Ветвитесь по типу или по `code`, никогда по тексту — тексты написаны для людей
и свободно правятся. Классы объявлены в `curlpro.errors` и импортируются из
самого `curlpro`; код, импортировавший их из приватного `curlpro._ffi`,
продолжает работать.

Мёртвое keep-alive соединение — не ошибка. Закрытие простаивающего
соединения сервером замечается, пока оно простаивает, и пул это соединение
больше не выдаёт; запрос, чьё переиспользованное соединение умерло до первого
байта ответа, уходит ещё раз по новому соединению при любом методе — ровно как
повторяет Chromium (`ShouldResendRequest`: соединение переиспользовано,
заголовков не пришло). Ответ, оборванный после первого байта, не повторяется —
сервер мог обработать запрос, — таймаут тоже. До 0.12 первый запрос после
keep-alive таймаута сервера по HTTP/1.1 падал каждый раз, а POST падал при
любом `retries=`.

Первый вопрос скрапера — повторять или нет, и иерархия на него отвечает:

```python
except curlpro.PermanentError:      # никогда не повторять: ответ не изменится
except curlpro.Timeout:             # повторить
except curlpro.CurlProError:        # всё прочее, обычно стоит одной попытки
```

У `PermanentError` два вида. `ProfileCapabilityError` (`profile_capability`) —
профиль этого не умеет: нет набора fetch, нет секции `http3`, нечего сузить в
ALPN, нет устройств; спросите :func:`capabilities` заранее или возьмите другой
профиль. `ConfigurationError` (`configuration`) — аргументы не сходятся:
незарегистрированное имя профиля, устройство не из списка, page не URL, имя
заголовка дважды. Раньше оба приходили обычным `CurlProError` без кода,
неотличимо от моргнувшей сети, и воркер, который повторял их трижды и терял
задачу, — это и есть причина, по которой они появились.

Ещё три класса несут то, по чему решает пул или цикл повторов. `ProxyError`
(`proxy`) — запрос провалил прокси, а не цель: `.stage` — `"dial"` (сам прокси
недоступен — TCP, или TLS у `https://`-прокси), `"auth"` или `"connect"`
(дозвонились, но туннель отвергнут или без ответа); `.status` — ответ прокси:
HTTP-статус на CONNECT или код ответа SOCKS5 (5 — «connection refused» *у
цели*), либо `None` при обрыве, который сохраняет свой код `proxy_closed`.
`ProxyAuthError` (`proxy_auth`) — стадия `"auth"`: 407 или отвергнутый логин
SOCKS5 — и одновременно `PermanentError`: тот же логин не пройдёт и в
следующий раз, повторы пропускаются. `CORSError` (`cors`) — отвергнутый
CORS-preflight (раздел 7) с `.status`, `.headers` и `.reason` ответа; не
постоянная намеренно — 503 на `OPTIONS` бывает минутным, отсутствующий
`Access-Control-Allow-Origin` — навсегда, и вызывающий различит их по
`.status` лучше, чем угадала бы библиотека. До 0.10 четыре исхода прокси были
одним `CurlProError` с пустым кодом, и пулы разбирали текст.

Коды: `timeout`, `expectation`, `profile_capability`, `configuration`,
`session_closed`, `too_large`, `ws_closed`, `ws_too_big`, `ws_protocol`,
`proxy_closed`, `proxy`, `proxy_auth`, `cors`. Ошибка без кода — обычный сбой с
причиной в тексте.

Три хука, каждый — список вызываемых в `s.hooks[...]`, добавляются и через
`@s.on_request`, `@s.on_response`, `@s.on_error`:

- **request** получает описание запроса — словарь с `method`, `url`, `headers`
  и остальным кадром — до отправки; может править его на месте или вернуть
  замену.
- **response** получает `Response` после прихода и может вернуть замену;
  ожидание проверяется по замене.
- **error** получает исключение неудавшегося запроса (сеть, таймаут,
  проваленное ожидание) и может вернуть исключение, которое поднять вместо
  него. Хук, который сам упал, не прячет исходный сбой: сбой отмечается на
  исключении, а остальные хуки всё равно выполняются.

## 10. Куки

`s.cookies` — отображение по имени для чтения и полная банка под ним:

| Вызов | Делает |
|---|---|
| `s.cookies["sid"]`, `.get`, `.keys`, `.items`, `.values` | значения |
| `.all()` | полные записи как словари `Cookie`: name, value, domain, path, expires (секунды эпохи, 0 у сессионной), флаги |
| `.set(name, value, *, domain, path="/", expires=0, secure=False, http_only=False, same_site="")` | добавляет одну; домен обязателен |
| `.load(list)`, `.export()` | простые записи внутрь и наружу |
| `.save(path)`, `.load_file(path)` | JSON; `load_file` читает и Netscape `cookies.txt`, распознавая по содержимому, а отсутствующий файл считает пустым первым запуском |
| `.save_netscape(path)`, `.load_netscape(path)`, `.to_netscape()` | тот `cookies.txt`, который используют curl, wget, yt-dlp и браузерные расширения |
| `.snapshot()`, `.restore(snapshot)`, `.transaction()` | механика отката |
| `.clear()` | забыть всё |

`r.cookies` у ответа — только то, что поставил этот ответ.

**Какие куки несёт запрос.** Банка подбирает по домену и пути; браузер задаёт
ещё два вопроса, и с 0.10 их задаёт и библиотека. Первый — режим credentials
из `fetch()` (`credentials=` на сессии или запросе): `same-origin`, умолчание
`fetch()` и XHR, шлёт куки только на собственный origin страницы — fetch на
другой origin *того же сайта* не несёт ничего; `include` шлёт их всюду, где
позволяют правила ниже; `omit` не шлёт. Второй — атрибут `SameSite` против
отношения страницы к URL, применяется только при заданном `page` (навигация
без инициатора считается same-site со своей целью, и уходит всё, как раньше):

| Кука | Same-site запрос | Cross-site fetch, XHR, субресурс | Cross-site навигация верхнего уровня |
|---|---|---|---|
| `SameSite=Strict` | идёт | — | — |
| `SameSite=Lax` | идёт | — | только GET и HEAD |
| `SameSite=None` (с `Secure`) | идёт | идёт, где семейство разрешает сторонние куки | идёт |
| без атрибута | идёт | Chromium: — (Lax по умолчанию); Firefox, Safari: как `None` | Chromium: на GET, и на POST, пока куке меньше двух минут (окно «Lax+POST»); Firefox, Safari: идёт |

Семейная часть — данные, `capabilities(name)["cookies"]`: Chromium считает куку
без атрибута Lax, отвергает `SameSite=None` без `Secure` при установке,
разрешает сторонние куки и сравнивает сайты со схемой; у Firefox нет Lax по
умолчанию, `None` без `Secure` он тоже отвергает и не шлёт кук вовсе на
cross-site fetch и субресурсы (Total Cookie Protection), с `include` или без;
строка Safari — документированный ITP WebKit, не захват; библиотечный профиль
(okhttp) политики не имеет и шлёт всё, что подобрано. Замерено на Chrome 153 и
Firefox 156: по пять кук на каждом из трёх сайтов и все виды запросов между
ними (`docs/STAGE18-RESULTS.md`). `samesite=False` на сессии возвращает
прежнее поведение — уходит всё подобранное, а `None` без `Secure` хранится —
для кода, который на него полагался. Запись куки несёт `created` (секунды
эпохи) для окна Lax+POST; импорт без него считается старым.

Тот же вопрос решает и обратное направление: **ответ на запрос без
credentials кук не ставит**. Fetch с `credentials="omit"` или с умолчанием
`same-origin` на другой origin кук не получает и поставить их не может —
иначе сайт, которому кук не показали, всё-таки поставил бы свои, и следующий
запрос с credentials понёс бы пару, которой браузер не производит (API,
ответивший на fetch без credentials собственной сессионной кукой, — третий
отчёт с прогона). Навигация credentials несёт всегда; CORS-preflight — никогда,
поэтому его `Set-Cookie` игнорировался и раньше. И импортированная кука с
IP-адресом в домене (`domain="127.0.0.1"`) хранится как host-only, какая она и
есть, — до 0.10.1 банка отвергала атрибут, и кука записывалась, но не
отправлялась.

на Chromium 152, чей захват она и воспроизводит), `safari-27-ios` (настоящий
User-Agent Safari на iOS 27.0 поверх захвата Safari 26) и `safari-27-macos`. Их
блок `source` имеет вид `derived` и называет опубликованный факт, на котором
стоит; как и транскрипция, они сообщают `measured: False` и поднимают
`transcribed_profile`, а живой захват заменит каждый, как только его браузер
окажется на стенде. Пометка может покрывать и часть профиля: у четырнадцати
профилей с транскрибированными SETTINGS стоит `source.covers =
["http2.settings"]`, и снятая дельта, приносящая свои SETTINGS, — Safari 16 и
17 стоят на Safari 15.5, — снова считается измеренной. Списки брендов у 41
транскрибированного профиля Edge, Opera и ранних Chrome у wreq-util были
неверны (скопированы между версиями, не закрыты кавычкой, потерян ведущий
пробел); теперь `sec-ch-ua` вычисляется так, как его вычисляет Chromium
(`scripts/chromium_brands.py`), — правило, которое подтверждает каждый снятый
профиль начиная с Chromium 105, и `tests/test_brands.py` сверяет с ним весь
корпус.

**Транскрибированные профили.** wreq-util описывает каждую версию браузера
кортежем опций BoringSSL и набором опций HTTP/2, версии наследуют кортеж друг
у друга прямо в исходниках; ни ClientHello, ни захвата кадров, ни хэшей там
нет. `scripts/transcribe-wreq.py` читает эти заявления об эквивалентности —
«Chrome 145 использует кортеж Chrome 142» — и там, где объявленный близнец
снят этим проектом, пишет новую версию дельтой от снятого профиля: снятые
ClientHello, кадры HTTP/2 и наборы заголовков, список брендов и
accept-language из wreq-util, User-Agent семейства с новой версией и блок
`source` с проектом, коммитом, файлом и тем, что именно взято. Версии, чей
кортеж не совпал ни с одной снятой, не включены (Chrome 105, Firefox
109/117/128, приватный и Android-Firefox, Chromium на Android и iOS); четыре
версии Safari стоят на снятой с одной изменённой настройкой HTTP/2 и говорят
об этом. Пометка видна на каждом уровне: `capabilities(name)["measured"]` —
`False`, `["source"]` говорит откуда, `s.fingerprint().measured` и `.source`
— то же, а `s.audit()` выдаёт `transcribed_profile` на каждой такой сессии в
любом режиме. Что значит пометка: ничего из того, что шлёт такой профиль,
этот проект на проводе не видел. Hello — настоящего браузера, той версии,
которую wreq-util называет близнецом; шлёт ли его на самом деле названная
версия — утверждение wreq-util, и часть его утверждений расходится с замерами
здесь, о чём написано в `note` профиля (Firefox 136–151 объявлены равными
135, хотя снятые здесь Firefox 155/156 отличаются; Safari 26.1–26.4 объявлены
равными 18.5, без постквантового key_share, который несёт 26.0; всякая Opera
объявлена с кодпоинтом ALPS от Chromium 131). Снятые профили транскрипция
никогда не перезаписывает: измеренная версия остаётся измеренной.

Что несёт каждое семейство, с учётом наследования:

| Семейство | Навигационный набор | Набор fetch | Набор HTTP/1.1 | WebSocket | HTTP/3 |
|---|---|---|---|---|---|
| Chrome, Edge, Yandex | да | измерен | да | да | chrome-151-windows, chrome-152-windows, chrome-152-android, yandex-26.8-android |
| Firefox, Tor | да | измерен | да | да | нет |
| Safari | да | **выведен** | да | нет | нет |
| okhttp | да | нет — у библиотеки нет fetch | нет | нет | нет |

`curlpro.capabilities(name)` отвечает на всё это по одному профилю, не открывая
сессии: какие наборы он несёт, какие протоколы умеет, какие устройства, отвечает
ли на `Accept-CH` и выведен ли его набор fetch.

**Набор fetch у Safari — единственное выведенное место в корпусе.** У
одиннадцати профилей Safari набора fetch не было вовсе, поэтому `mode="fetch"`
на них отклонялся и XHR они сделать не могли — а пользователь сообщил, что
Safari проходит его антибот примерно вдвое чаще любого Chrome и именно поэтому
непригоден. `scripts/gen-safari-fetch.py` выводит набор из стандарта Fetch и
собственного навигационного набора профиля: `accept: */*`, без
`upgrade-insecure-requests` и `sec-fetch-user`, `sec-fetch-mode: cors`,
`sec-fetch-dest: empty`, слоты для `Origin`, `Referer` и заголовков тела — а у
профилей 15.x вовсе без `sec-fetch-*`, потому что WebKit выпустил Fetch
Metadata в Safari 16.4, и выдумать их было бы хуже, чем отсутствующий набор.
**Состав** надёжен, **порядок** — догадка, а порядок входит в отпечаток.
Поэтому это помечено: `capabilities()["derived_fetch"]` истинно, а `audit()`
выдаёт `derived_fetch_set`, когда такой набор действительно используется.
Заменить захватом, как только под рукой окажется Mac или iPhone.

**Мобильные.** `chrome-152-android` и `yandex-26.8-android` несут пул из 46
настоящих телефонов — точные строки `ro.product.model` из каталога устройств
Google Play на правдоподобных версиях Android. `device="Pixel 8"` или
`device="random"` выбирает один на сессию. Модель едет в client hints
`sec-ch-ua-model` и `sec-ch-ua-platform-version`, которые уходят только после
того, как сайт попросил их через `Accept-CH` (и сразу при `Critical-CH`), и — на
обоих профилях — в строке User-Agent, так что пул — 46 разных строк. У Яндекса
так делает сам браузер. У Chrome это намеренное отступление, решение владельца
проекта: стоковый Chrome ≥110 шлёт сокращённое `Android 10; K` для любого
телефона и раскрывает модель только в подсказках, и защита, знающая о
сокращении, отличит несокращённую строку. Без устройства профиль уходит как
снят, с сокращённой строкой. Свой список передаётся в
`devices=[{"name": ..., "model": ..., "platform_version": ...}]`. Имя не из
списка отклоняется.

**Настольные личности.** С 0.11 настольные Chromium 151–153
(`chrome-151…153-windows/macos/linux`) несут то, чем настоящие пользователи
одной версии браузера различаются помимо телефона: на Windows — выпуск системы
(`sec-ch-ua-platform-version` — это версия UniversalApiContract: `10.0.0` у
Windows 10 22H2, `14.0.0`/`15.0.0`/`19.0.0` у Windows 11 22H2/23H2/24H2),
точная сборка в `sec-ch-ua-full-version` и внутри `-full-version-list`
(стабильные выпуски по chromiumdash) и то, 32-битный ли процесс у браузера
(`sec-ch-ua-wow64`); на macOS — версия системы и процессор
(`sec-ch-ua-arch: "arm"` на Apple silicon, `"x86"` на Intel); на Linux — только
сборка, потому что версию платформы Chromium там шлёт пустой. Те же профили
получили секцию `client_hints`, которой у них не было, снятую на Chrome 153 /
Windows 10 (`docs/STAGE19-RESULTS.md`): одиннадцать подсказок в том порядке
навигации, который Chrome держит со второй страницы, и порядок fetch из захвата
Pixel. Профили Safari на iOS несут версии iOS своей линейки Safari — Safari 18
пишет версию дважды (`iPhone OS 18_1_1`, `Version/18.1.1`), Safari 26 заморозил
токен системы на `18_7` и настоящую версию пишет только в `Version/26.0.1`, как
показывает живой трафик, — а профили Firefox на Linux — токен `Ubuntu; `,
который несут некоторые сборки. `device="random"` выбирает одну личность на
сессию, как на Android, и `fingerprint().device` её называет; без `device=`
профиль шлёт значения машины захвата (Windows 10 22H2, сборка 153.0.8010.52,
32-битный Chrome — на `chrome-153-windows`), в остальных — первую личность
пула, а на Safari и Firefox — снятую строку. TLS не двигается. Зерно —
`scripts/identities.json`, у каждого списка свой источник;
`scripts/gen-identities.py` пишет профили, а `--check` роняет CI при
расхождении. У `edge-153-windows` пула нет: Edge пишет в список свою сборку
рядом со сборкой Chromium, и ни та, ни другая здесь неизвестны без настоящего
Edge на стенде. У macOS-профилей Safari его тоже нет: настольная строка на
любом Mac говорит `10_15_7`, подсказок Safari не шлёт, и в HTTP один Mac —
любой другой.

**Что лежит в пуле.** `capabilities(name)["device_kind"]` и
`fingerprint().device_kind` говорят, что такое устройства: `"phone"` (модель и
её Android), `"desktop"` (выпуск Windows или macOS, процессор и сборка Chrome),
`"iphone"` (версия iOS) или `"distro"` (токен дистрибутива Linux), и `""` у
профиля без пула. До 0.11 любой пул состоял из телефонов, и код, читавший «есть
устройства» как «это телефон», был прав; 0.11 изменила это без единого слова в
API (отчёт с боевого прогона), и это поле — способ спросить. Пулы обновлены
26.09.2026: вышедшие с тех пор сборки Chrome 153, сборки Chrome 154 для его
выведенных профилей, macOS 27.0 и версии macOS в трёхчастной форме, которую
шлёт Chromium (`15.7.0`, никогда не `15.7`, — `user_agent_utils.cc`
форматирует `%d.%d.%d`); Safari 26.0 на iOS замораживает токен ОС на `18_6`,
26.0.1 и позже — на `18_7`.

**Наследование.** Профиль может назвать `based_on`; тогда он хранит только свои
отличия. Chrome 110 поверх Chrome 98 — одна строка: включить перемешивание
расширений. `Profile.from_file(path).derive("chrome-153-windows",
headers={...}).register()` делает дельту из Python; `register_profile()`
принимает dict, JSON-строку или bytes. Схема — в `docs/PROFILE-SCHEMA.md`.

**Захват браузера** — Go-команда, не часть колеса: `go build ./cmd/curlpro`,
затем `curlpro capture -name firefox-155-windows` поднимает стенд, ведёт
установленный браузер, сворачивает несколько образцов в профиль и даёт полному
профилю наборы HTTP/1.1, fetch и WebSocket его семейства. `validate`, `diff`,
`collapse` и `list` — остальные подкоманды; метод и грабли — в
`docs/CAPTURE.md`.

## 12. Транспорты: HTTP/1.1, HTTP/2, HTTP/3, WebSocket

Между HTTP/1.1 и HTTP/2 выбирает сервер через ALPN из списка, который предлагает
профиль; `force_http1` сужает предложение. У каждого транспорта свой набор
заголовков из профиля: HTTP/1.1 добавляет `Host` и `Connection` и использует
регистр браузера; Chrome не шлёт там `priority`, а Firefox — `TE`.

HTTP/3 включается как у браузера — сначала TCP, потом QUIC после заголовка
`Alt-Svc` — или сразу через `http3=True`; `protocol="h3"` заставляет один
запрос. Транспортные параметры QUIC, SETTINGS, GREASE-кадр и порядок заголовков
берутся из секции `http3` профиля, сверенной с `quic.browserleaks.com`. Секция
есть у четырёх профилей (раздел 11).

WebSocket: `with s.websocket(url, headers=None, subprotocols=None, timeout=30.0,
max_message_size=0) as ws`. Заголовки рукопожатия берутся из шаблона
`websocket` профиля — набор и порядок, которые шлют Chrome и Firefox, включая
`permessage-deflate`. `ws.send(str | bytes)` выбирает тип кадра по данным,
`ws.recv()` возвращает `str` или `bytes`, `ws.ping()`, `ws.close(code=1000,
reason="")`, а `for message in ws` читает, пока сервер не закроет
(`WebSocketClosed`). `timeout` — предел тишины на чтении (код `timeout`,
соединение остаётся рабочим); `max_message_size` поднимает `ws_too_big`.
Открытый `ws://` тоже работает.

## 13. Потоки, загрузки, async

```python
with s.stream("GET", url) as r:                 # те же аргументы, что у request()
    for chunk in r.iter_content(64 * 1024):
        out.write(chunk)
    for line in r.iter_lines():                 # NDJSON и подобное
        ...
```

Поток держит соединение до закрытия, отсюда `with`. `r.read()` собирает
остаток и ограничен `max_response_size`, если он задан; `iter_content()` — нет,
намеренно. У `AsyncSession` чтение куска или приём WebSocket, отменённые
`asyncio.wait_for`, продолжаются и отдают данные следующему вызову — раньше
таймаут простоя их терял, — а незакрытый поток или сокет закрывается при сборке
мусора.
Закрытие с непрочитанным телом рвёт соединение, а не дочитывает. Загрузки идут
потоком через `body_file=path`.

`AsyncSession` принимает те же аргументы, что `Session`, и предлагает те же
методы как корутины: `await s.get(...)`, `async with s.stream(...) as r: async
for chunk in r.iter_content()`, `async with s.websocket(url) as ws`. Запрос — это
горутина на нативной стороне; процесс держит один поток, и цикл событий никогда
не блокируется. Отменённая задача отменяет запрос нативно. `s.cookies`,
`s.headers` и хуки — те же, что у синхронной сессии.

## 14. Отпечаток, аудит и персоны

`s.fingerprint(url="https://example.com/")` считает, ничего не отправляя, что
увидел бы сервер:

| Поле | Значение |
|---|---|
| `ja4`, `ja4_r` | JA4 и его читаемая форма — стабильны между соединениями и доменами; это значение для сравнения |
| `ja3n`, `ja3`, `ja3_text` | JA3 с отсортированными расширениями (стабилен) и обычный JA3, который **плавает** между соединениями у Chrome ≥110, потому что расширения перемешиваются |
| `akamai` | отпечаток HTTP/2: SETTINGS, window update, priority, порядок псевдозаголовков |
| `ciphers`, `extensions`, `curves`, `sigalgs`, `alpn` | сырые списки без GREASE, в порядке отправки |
| `headers`, `headers_http1` | имена заголовков, которые ушли бы у обычного GET, по HTTP/2 и по HTTP/1.1 |
| `ja4h`, `ja4h_http1`, `ja4h_available` | отпечаток запроса; пуст с `ja4h_available == False` в сборке с `-tags nofoxio` |
| `user_agent`, `profile` | строка, которая ушла бы, и имя профиля |
| `to_dict()["mode"]`, `["modes_used"]`, `["derived_fetch"]` | набор, с которым собрано превью; наборы, с которыми запросы реально ушли; выведен ли fetch-набор (раздел 11) |
| `client_hello` | собранный ClientHello байтами; `len()` отвечает, влезает ли он в один TCP-сегмент |
| `to_dict()`, `diff(other)`, `==` | всё как данные; разница по полям (расширения сравниваются как множества, `ja3` и `client_hello` исключены) |

Значения сверены с 50 живыми захватами в `reference/baselines`: JA4, JA3N и
строка Akamai совпадают с оракулом на каждом. Собственные опции сессии
учитываются — `force_http1` и `post_quantum=False` меняют hello, и отпечаток
показывает тот hello, который эта сессия шлёт.

`s.audit()` ищет противоречия внутри личности — причину, по которой правильный
отпечаток всё равно ловят. У каждого `Finding` есть `code`, `level` (`high`,
`medium`, `low`), `what`, `why`, `fix`. Проверки консервативны; стоковый
профиль молчит, кроме телефонного профиля без выбранного устройства:

| Код | Уровень | Срабатывает, когда |
|---|---|---|
| `tor_language` | high | профиль Tor шлёт любой `accept-language`, кроме `en-US,en;q=0.5` |
| `ua_version` | high | версия в User-Agent расходится с версией профиля (Chrome, Edge, Firefox) |
| `ua_family` | high / medium | User-Agent другого браузера или вовсе без браузера |
| `platform` | high | `sec-ch-ua-platform` расходится с User-Agent |
| `mobile_no_device` | medium | профиль со списком устройств и без выбранного |
| `navigation_headers_on_fetch` | high | `sec-fetch-user` или `upgrade-insecure-requests` рядом с fetch-метаданными, говорящими «fetch» |
| `accept_encoding` | medium | `accept-encoding` не как у профиля или его нет вовсе |
| `no_user_agent` | high | нет User-Agent вообще — то, что оставляет `default_headers=False` |
| `referer_site` | high | Referer расходится с fetch-метаданными или с Origin рядом: рукописный Referer при `sec-fetch-site: none`, Referer с чужого origin при `same-origin`, либо Origin и Referer называют две разные страницы |
| `transcribed_profile` | medium | профиль транскрибирован из описания другого проекта (раздел 11): ничего из того, что он шлёт, здесь на проводе не видели. Срабатывает в любом режиме; `capabilities(name)["measured"]` говорит то же без сессии |
| `derived_fetch_set` | medium | сессия шлёт выведенный набор fetch у Safari, чей порядок не измерялся (раздел 11) — судя по наборам, с которыми её запросы реально ушли, а не только по режиму конструктора; `s.audit(mode="fetch")` спрашивает до того, как ушёл хоть один |

`Persona` связывает одну личность — профиль, прокси, устройство, заголовки
(включая удаления), куки, произвольные `notes` — с одним JSON-файлом:

```python
p = curlpro.Persona.new("chrome-152-windows", proxy="socks5h://user:pw@host:1080",
                        headers={"Accept-Language": "de-DE,de;q=0.9"})
p.save("accounts/user42.json")

p = curlpro.Persona.load("accounts/user42.json")
with p.session(timeout=20) as s:       # переопределения уходят в Session; куки восстановлены
    s.get("https://example.com/")     # забираются на выходе, даже если блок упал
p.save()                              # атомарная запись; усечённый файл при загрузке отклоняется
```

`s.headers_for(...)` отдаёт имена HTTP/1.1 в регистре провода — `Host`,
`User-Agent`, `sec-ch-ua`, как их пишет профиль, — и сам берёт эту форму для
`http://`-адреса, где другого транспорта нет; для `https://` превью по умолчанию
в форме HTTP/2, `protocol="http1"` просит другую.

`p.open()` возвращает обычную сессию, `p.capture(s)` забирает куки сессии, не
закрывая её, `p.fingerprint()` и `p.audit()` работают без сети,
`load_all(directory)` перебирает папку персон. Персона ничего не ротирует: какую
личность брать и когда её списывать — политика вызывающего.

## 15. Что не нужно переписывать

Ассистенту, которого просят добавить что-то из этого в код, уже использующий
curlPro, стоит взять готовое. Каждая строка его называет:

- **Распаковка** `gzip`, `deflate`, `br`, `zstd`, наложенных в любом порядке — `r.content` уже распакован.
- **Определение кодировки** — `r.text` и `r.encoding` следуют браузерному порядку: заголовок, BOM, документ.
- **Редиректы** с историей и отказом https→http — `allow_redirects`, `r.history`, `r.url`.
- **Ретраи** с экспоненциальной паузой, `Retry-After` и идемпотентностью — `retries=`, `retry_statuses=`, `retry_methods=`.
- **Хранение кук**, `cookies.txt`, откат — `s.cookies.save/load_file`, `transaction()`, `rollback_cookies=`.
- **Порядок и регистр заголовков** — профиль, плюс `header_order=[..., ...]` для правок; никогда не собирайте списки заголовков руками.
- **Удаление заголовка** — `None`, а не `default_headers=False`.
- **Наборы fetch и навигации** — `mode`, выбирается сам.
- **Referer, Origin и sec-fetch-site для запроса со страницы** — `page=` на сессии или запросе, а не рукописный `Referer`.
- **Client hints, модели телефонов и настольные личности** — `device=`, `devices=`, уже отвечают на `Accept-CH` и `Critical-CH`.
- **Прокси** с переменными окружения, SOCKS5 с удалённым DNS, аутентификация CONNECT — `proxy=`, `trust_env`.
- **HTTP/3** с `Alt-Svc` и откатом — включён по умолчанию там, где у профиля есть секция.
- **WebSocket** с рукопожатием браузера и `permessage-deflate` — `s.websocket()`.
- **Потоковые** загрузки и выгрузки — `s.stream()`, `body_file=`.
- **Проверка ответа** — `Expect(...)` вместо самописных цепочек `if`.
- **Файлы личностей** — `Persona`, а не самодельный JSON из прокси и кук.
- **Проверка отпечатка** — `s.fingerprint()` и `s.audit()` офлайн, а не обращение к оракулу.
- **Посмотреть уходящие заголовки** — `s.headers_for(method, url, mode=..., page=...)`, а не свой эхо-сервер.
- **CORS-preflight** — библиотека сама шлёт, проверяет и кэширует его перед каждым непростым кросс-origin fetch со страницы; `s.preflight_for(...)` показывает его. Никогда не `s.options()` с кастомными заголовками на нём.
- **Какие куки несёт кросс-origin запрос** — `credentials=` и правила SameSite, применённые от `page=`; никогда не отфильтрованный руками `Cookie`.
- **Отличить мёртвый прокси от отвергнутого туннеля и от 407** — `ProxyError.stage` и `.status`, `ProxyAuthError`; никогда не подстрока сообщения.
- **Спросить, умеет ли профиль что-то** — `curlpro.capabilities(name)`, а не пробный запрос и подстрока в тексте ошибки.
- **Выбрать профили для ротации** — `list_profiles(measured=True)`; транскрибированный профиль (`capabilities(name)["measured"] == False`) — утверждение другого проекта, и аудит об этом говорит.
- **Отличить безнадёжный отказ от временного** — `except curlpro.PermanentError`, а не сверка сообщения.
- **Прочитать данные профиля** — `curlpro.get_profile(name).data`, а не JSON внутри `site-packages`.
- **Прослойка под `requests`** — `import curlpro.requests as requests` уже есть; неподдерживаемые аргументы поднимают ошибку, а не игнорируются.
- **Новая версия браузера** — дельта профиля или `register_profile()`, а не правка библиотеки.

## 16. Проверенные утверждения: что было ложью, что правда

Всё в этом руководстве сверено с кодом, профилями и набором тестов 16 сентября
2026 года. Ревизия старых документов нашла ложными эти утверждения, и они
исправлены в том же релизе:

- README говорил, что документация проекта написана по-русски, а английский
  файл — её двойник. Ложь с 8 сентября 2026: оригинал английский, а
  `README.ru.md` — двойник; тест держит их структуру в согласии.
- Список кодов ошибок в README не содержал `too_large` и `proxy_closed`,
  которые нативная сторона поднимает с 0.3 и 0.5.2 соответственно.
- Абзац о лицензиях в README называл fhttp MIT; он под BSD-3-Clause, как
  говорит `NOTICE`.
- `ARCHITECTURE.md` называл текущим релизом 0.4.2.
- `curlpro.request(method, url)` был описан по форме, но не экспортирован;
  теперь экспортирован.

Факты, в которых легко усомниться и которые верны:

- Chrome ≥110 перемешивает TLS-расширения на каждом соединении, поэтому `ja3`
  плавает, а `ja4` и `ja3n` стоят. Это правильное поведение, а не дефект.
- ClientHello современного браузера — ~1,9 КБ из-за постквантового key_share
  и занимает два TCP-сегмента. Профили это воспроизводят, а
  `post_quantum=False` — ручка для проверки путей, которым это не нравится.
- Firefox 155 шлёт три key_share (X25519MLKEM768, x25519, secp256r1); профиль
  воспроизводит сырой hello, снятый с живого браузера.
- HTTP/2 SETTINGS 14 профилей корпуса до 0.12 были пустыми — их сигнатуры не
  записали кадр SETTINGS, — теперь это значения wreq-util с пометкой
  `source.covers`; эталоны перезаписаны с browserleaks.
- 41 транскрибированный список брендов у wreq-util был неверен; `sec-ch-ua`
  вычисляется так, как его вычисляет Chromium, и с этим согласен каждый захват
  начиная с Chromium 105.
- 238 профилей транскрибированы из wreq-util, и каждый об этом говорит
  (раздел 11): транскрипция никогда не строит собственный hello, только
  указывает версии на снятого близнеца, которого называет источник. Это
  первые данные в корпусе, которых проект не видел на проводе, и
  `list_profiles(measured=True)` — список без них.
- Четыре профиля выведены из живых Windows-захватов, а не сняты сами:
  `edge-153-windows` — это `chrome-153-windows` с User-Agent и списком брендов
  Edge, а `chrome-151-macos`, `chrome-152-macos`, `chrome-153-macos` —
  Windows-захваты с macOS в User-Agent и `sec-ch-ua-platform`. Основание: в
  каждой паре Chrome/Edge и каждой паре Linux/macOS, что есть в корпусе
  (Chrome с 98 по 120), JA3N, строка Akamai и порядок заголовков совпадают, а
  различаются только User-Agent и список брендов — ClientHello и HTTP/2
  задаёт BoringSSL и сетевой стек Chromium, а не ОС и не оболочка. Edge 153
  стоит на машине захвата, но его headless-режим до стенда не дошёл (три
  запуска, ни одного образца), так что дельта — данные, а не захват, и живой
  прогон её заменит. Baseline у каждого выведенного профиля доказывает лишь
  согласованность реплея, а не то, что браузер шлёт именно это.
- Chrome 153 добавил TLS-расширение, которого uTLS не знает, — `0xca34`,
  черновик trust-anchor identifiers, 186 байт — к набору Chrome 152; профиль
  воспроизводит его сырыми байтами (`allow_blunt_mimicry`). JA4 тот же, что у
  152 (для JA4 набор расширений тот же), JA3N другой. Снят живьём 22 сентября
  2026, пять образцов, HTTP/2 идентичен 152.
- Firefox 156 отбросил обе группы FFDHE (ffdhe2048, ffdhe3072) из
  `supported_groups`: пять групп вместо семи, hello на четыре байта короче,
  тот же JA4 (группы в него не входят) и другой JA3N. Снят живьём 21 сентября
  2026, пять образцов; всё остальное — настройки HTTP/2, наборы заголовков —
  совпало с Firefox 155 и наследуется от него.
- postman-echo.com стоит за Cloudflare, который переписывает `Accept-Encoding`
  в `gzip, br` до того, как origin его отдаст. Судите о заголовках по сырому
  стенду (`python/tests/rawserver.py`), а не по публичному эхо.
- Любой кастомный заголовок переключает запрос на набор fetch в режиме `auto`.
  Так делает браузер; `mode="navigate"` говорит иначе.
- `timeout` ограничивает весь запрос, а не тишину между байтами, как в
  `requests`. Перенесённое значение безопасно: строже, а не мягче.
- ClientHello возобновлённого соединения — не первый: он несёт
  `pre_shared_key` в конце, а Firefox убирает из него `session_ticket`.
  Измерено на обоих браузерах и воспроизведено; ни один из них не предлагает
  early data на возобновлённом TCP-соединении, даже серверу с поддержкой 0-RTT.

## 17. Указатель API

| Имя | Вид | Одной строкой |
|---|---|---|
| `Session` | класс | один профиль, переиспользуемые соединения, память и политика |
| `AsyncSession` | класс | то же поверх asyncio, нативная конкурентность |
| `Response`, `Redirect`, `Preflight` | класс | ответ; один хоп цепочки редиректов; CORS-preflight, который его предварял |
| `StreamResponse`, `AsyncStreamResponse` | класс | тело, читаемое кусками |
| `WebSocket`, `AsyncWebSocket` | класс | открытый WebSocket |
| `Cookies`, `Cookie` | класс | банка и одна запись |
| `Expect`, `ExpectationFailed` | класс | ожидание от ответа и его провал |
| `Fingerprint` | класс | что видит сервер, посчитано офлайн |
| `Finding`, `audit(target)` | класс, функция | одно противоречие; проверка сессии или персоны |
| `Persona`, `load_all(dir)` | класс, функция | личность между запусками; папка с ними |
| `Profile` | класс | профиль как объект: `from_file`, `derive`, `register`, `save` |
| `load_profiles(dir)`, `register_profile(x)`, `list_profiles()`, `ensure_loaded()` | функция | управление профилями |
| `capabilities(name)`, `get_profile(name)`, `library_version()` | функция | что умеет профиль (включая `measured` и `source`), профиль как данные, версия нативной библиотеки |
| `list_profiles(measured=None)` | функция | все профили; `True` — только снятые, `False` — только транскрибированные |
| `s.headers_for(method, url, ...)` | метод | заголовки, которые понесёт запрос, без отправки |
| `s.preflight_for(method, url, ...)` | метод | CORS-preflight, которым будет предварён запрос, или `None` |
| `request`, `get`, `post`, `put`, `patch`, `delete`, `head`, `options` | функция | один запрос в своей сессии; `impersonate=` выбирает профиль |
| `CurlProError`, `Timeout`, `HTTPError`, `WebSocketClosed` | исключение | иерархия; `.code` у всех; объявлены в публичном модуле `errors` |
| `errors` | модуль | классы исключений, импортируемые отсюда или из `curlpro` |
| `Headers` | класс | заголовки ответа: `dict[str, list[str]]` с поиском без учёта регистра и `.first(name)` |
| `RequestKwargs` | тип | ключевые аргументы глаголов запроса, для `Unpack` в сигнатуре обёртки |
| `DEFAULT_MAX_RESPONSE_SIZE` | константа | 100 МиБ: предел тела буферизованного ответа, когда `max_response_size` не задан |
| `PermanentError`, `ProfileCapabilityError`, `ConfigurationError` | исключение | отказы, которых не лечит повтор (раздел 9) |
| `ProxyError`, `ProxyAuthError`, `CORSError` | исключение | отказ прокси со `.stage` и `.status`; постоянный 407; отвергнутый CORS-preflight с его ответом |
| `curlpro.requests` | модуль | лицо в стиле `requests`: `get`, `Session`, `status_code`, те же исключения |
