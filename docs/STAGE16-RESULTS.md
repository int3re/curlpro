# Этап 16 — закрытие оставшихся долгов и keep-alive

Дата: 2026-09-03. Продолжение [STAGE15](STAGE15-RESULTS.md): закрыты долги,
которые там остались, и добавлена опция `keep_alive` у сессии.

Главное за этап:

- порядок заголовков в HTTP/3 впервые **наблюдается** — и первый же замер
  нашёл расхождение с Chrome, которое жило с этапа 7;
- `Proxy-Authorization` больше не уходит без спроса: CONNECT повторяется
  после 407, как у браузера;
- `permessage-deflate` сжимает и при окне меньше 32 КиБ;
- два профиля корпуса были нерабочими: `pre_shared_key` на свежем соединении;
- `keep_alive=False` выключает переиспользование соединений.

## 1. keep-alive: сначала замер, потом опция

Запрос звучал как «сделай, чтобы не пересоздавал соединения». Первым делом
проверено, пересоздаёт ли:

```
=== RUN   TestConnectionReusedBetweenRequests/http1
=== RUN   TestConnectionReusedBetweenRequests/http2
--- PASS: TestConnectionReusedBetweenRequests (0.03s)
```

Пять последовательных запросов укладываются в **одно** TCP-соединение на обоих
транспортах. Переиспользование работало и раньше — не хватало выключателя,
он и добавлен:

```python
with curlpro.Session(keep_alive=False) as s:   # соединение на запрос
```

В Go это `Options.DisableKeepAlive` — полярность как у
`net/http.Transport.DisableKeepAlives`, чтобы нулевое значение сохраняло
обычное поведение. Соединение не кладётся в пул вовсе, и `release` закрывает
его сразу после ответа.

**Заголовок `Connection: close` при этом не отправляется.** Браузер его не
шлёт; отправив, мы выдали бы себя ровно там, где стараемся не выделяться.
Клиент просто закрывает сокет — так же, как браузер закрывает простаивающий.

| Проверка | Результат |
|---|---|
| `TestConnectionReusedBetweenRequests` | 5 запросов → 1 соединение (h1 и h2) |
| `TestKeepAliveDisabledOpensConnectionPerRequest` | 3 запроса → 3 соединения, пул пуст |
| `TestKeepAliveDisabledKeepsProfileConnectionHeader` | на проводе `Connection: keep-alive` |
| `test_keepalive.py` | то же через Python, на сервере сырых заголовков |

Версия ABI поднята до `0.4.0`. По правилу из `lib/curlpro.go` минор растёт,
когда Python начинает зависеть от нового поля конфигурации: `mode` из этапа 15
въехал без поднятия — исправлено вместе с `keep_alive`.

## 2. Новый стенд: cmd/hcapture

Порядок заголовков HTTP/3 не показывал ни один оракул, и это был единственный
транспорт, где профиль верили на слово. Стенд [cmd/hcapture](../cmd/hcapture)
закрывает пробел: он поднимает TLS с ALPN `h2` и QUIC с ALPN `h3` на одном
адресе, разбирает HEADERS-кадры вручную (HPACK для HTTP/2, свой
[internal/qpack](../internal/qpack) для HTTP/3) и печатает имена в порядке
провода. Страница сама делает `fetch`, XHR и переход по ссылке, так что за один
запуск снимаются оба набора.

```bash
go run ./cmd/hcapture -auto              # HTTP/2
go run ./cmd/hcapture -auto -h3          # HTTP/3
```

Две вещи, на которых это едва не встало:

- **Chrome ходит на `localhost` по `::1`.** Слушатель только на `127.0.0.1`
  не получает ни одной датаграммы. Та же ловушка была при снятии QUIC
  ClientHello — теперь `resolveAll` занимает все адреса имени.
- **`--ignore-certificate-errors` не распространяется на QUIC.** Датаграммы
  Chrome шлёт, рукопожатие молча бросает, `Accept` не срабатывает никогда.
  Разбирается счётчиком датаграмм: «браузер не пришёл» и «пришёл, но
  рукопожатие не сложилось» — разные вещи. Лечится
  `--ignore-certificate-errors-spki-list` с отпечатком ключа стенда;
  hcapture считает его сам из `capture/certs/tls.crt`.

## 3. Замер Chrome 152: HTTP/2 и HTTP/3

Совпало всё, кроме одного — и это одно оказалось багом.

### Что подтвердилось

| Что | Замер |
|---|---|
| порядок псевдо-заголовков | `m,a,s,p` на обоих транспортах |
| навигация | `sec-ch-ua`, `sec-ch-ua-mobile`, `sec-ch-ua-platform`, `upgrade-insecure-requests`, `user-agent`, `accept`, `sec-fetch-*`, `accept-encoding`, `accept-language`, `cookie`, `priority` |
| fetch/XHR | `content-length`, `sec-ch-ua-platform`, `user-agent`, `sec-ch-ua`, `content-type`, **кастомные**, `sec-ch-ua-mobile`, `accept`, `origin`, `sec-fetch-*`, `referer`, `accept-encoding`, `accept-language`, `cookie`, `priority` |
| `priority` в наборе fetch | есть, значение `u=1, i`, последним — догадка из известных захватов подтвердилась |
| позиция `cookie` | после `accept-language`, перед `priority` — и в навигации, и в fetch |
| HTTP/3 против HTTP/2 | порядок совпадает имя в имя во всех четырёх случаях |

Профиль `chrome-151-windows` описывал это верно — правок не потребовалось.

### Что разошлось: Content-Length в HTTP/3

Сверка своего клиента с Chrome на одном стенде (`fetch` с телом):

```
chrome: :method :authority :scheme :path content-length sec-ch-ua-platform … priority
наш:    :method :authority :scheme :path sec-ch-ua-platform … priority content-length
```

На HTTP/2 позиция бралась из порядка профиля, на HTTP/3 — нет: апстримный
`request_writer.go` пропускал `content-length` в общем цикле и дописывал его
последним. В `req.Header` этого заголовка нет вовсе — его добавляет транспорт,
а профиль держит под него пустой слот.

Исправлено `withSlot` в [internal/h3/order.go](../internal/h3/order.go):
имя встаёт на позицию из `HeaderOrderKey`, даже когда самого заголовка
в запросе нет. Повторный замер против живого Chrome — совпадение.

Расхождение было заметным: сервер, сравнивающий два транспорта одного клиента,
видел разный порядок там, где Chrome даёт одинаковый.

### Что расходится намеренно

- `Referer` браузер подставляет из контекста страницы, у библиотеки его нет.
  Задаётся вызывающей стороной, слот в профиле для него есть.
- `sec-fetch-user: ?1` мы шлём всегда, Chrome — только для навигации,
  начатой человеком (переход из JS его не содержит). Наш случай — «адрес
  открыт пользователем», для него `?1` верно; гасится `SuppressHeaders`.

## 4. CONNECT: авторизация только после 407

Было: `Proxy-Authorization` уходил в первом же CONNECT. Chrome шлёт CONNECT
без учётных данных, получает 407 и повторяет. Прокси, ведущий журнал, видел
у нас не браузер.

Стало: первый CONNECT уходит пустым; на 407 клиент повторяет с учётными
данными. Соединение переиспользуется, если прокси его держит и тело ответа
дочитано; иначе сокет открывается заново — многие прокси закрываются вместе
с 407.

```
--- PASS: TestConnectSendsCredentialsOnlyAfterChallenge/прокси_держит_соединение
--- PASS: TestConnectSendsCredentialsOnlyAfterChallenge/прокси_закрывает_после_407
```

Цена — один лишний круг до прокси на каждое соединение. Видно это только
самому прокси, но именно он и классифицирует клиентов.

## 5. permessage-deflate: окно меньше 32 КиБ

`compress/flate` не умеет окна меньше 32 КиБ, поэтому при
`client_max_window_bits < 15` исходящие сообщения уходили **несжатыми**.
RFC это разрешает, но Chrome сжимал бы, и разница видна серверу на каждом
кадре — бит RSV1.

Компрессор теперь берётся у `klauspost/compress` (`NewWriterWindow`), когда
окно меньше стандартного; для обычных 15 бит остаётся `compress/flate`.

Проверка написана так, чтобы её нельзя было пройти случайно: сервер в тесте
свой, он смотрит RSV1 и разжимает `zlib` с `wbits=-9`. Сообщение, сжатое окном
32 КиБ, такой декодер не примет. Контрольный прогон со старым кодом:

```
FAILED test_small_client_window_is_compressed_within_window
  сообщение ушло несжатым, хотя расширение согласовано
```

С исправлением — два теста из двух зелёные.

## 6. Корпус: три несогласованных файла

Долг тянулся с этапа 3. Разобран по одному, и два случая оказались не
«несогласованностью документа», а нерабочими профилями.

| Профиль | Что было | Что сделано |
|---|---|---|
| `chrome-119-macos` | `pre_shared_key` вместо `padding` | заменено на `padding` |
| `chrome-120-macos` | то же | заменено на `padding` |
| `chrome-133-macos` | ALPS `17613` против `17513` в `ja3n_text` | подтверждено своим захватом ещё на этапе 3, правок нет |
| `chrome-131-android` | `supported_groups` без X25519MLKEM768 | оставлено: источник истины — сам захват, а не производное поле |

`pre_shared_key` появляется только при возобновлении сессии. На свежем
соединении расширение пустое, и uTLS отказывается его слать:

```
$ go run ./cmd/probe -profile chrome-119-macos
ошибка: TLS handshake: tls: empty psk detected; remove the psk extension
```

Библиотека это скрывала: `OmitEmptyPsk: true` выбрасывает пустой PSK молча.
В результате профиль не падал, но и `padding` не слал — то есть отличался
от собственного близнеца `chrome-119-linux`, снятого с обычного соединения.
После правки оба дают один и тот же набор значений JA4.

Попутно: `chrome-131-android` объявлял `sec-ch-ua-mobile: ?0` при
UA `… Mobile Safari/537.36`. Chrome на Android шлёт `?1` — как и соседний
`chrome-99-android`. Исправлено.

### JA4 колеблется, и это правильно

Профили с `padding` дают **два** значения JA4: BoringSSL добавляет
выравнивание только когда длина ClientHello попадает в нужный диапазон,
а длина плавает из-за GREASE ECH. Замер на публичном оракуле, 4 прохода:

| Профиль | значений JA4 |
|---|---|
| `chrome-119-linux`, `chrome-119-macos`, `chrome-120-macos`, `edge-120-linux` | 2 |
| остальные 7 профилей с `padding` | 1 |

Формат эталона это предусматривает — `ja4` там список допустимых значений.
Эталоны исправленных профилей дополнены вторым значением, иначе проверка
по расписанию падала бы через раз.

## 7. Что осталось и почему

| Долг | Почему не закрыт |
|---|---|
| Слоты POST, набор fetch и рукопожатие WebSocket у Safari | Safari нет на машине замера. Закрывается на macOS одним прогоном: `go run ./cmd/hcapture` без `-auto` и открыть `https://localhost:8443/` руками |
